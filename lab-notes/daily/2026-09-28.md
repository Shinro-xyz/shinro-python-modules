# 2026-09-28 — SIMD column-sweep `matmul` + wide-n coverage

Branch: `main`

## Why

`matmul` (the 2D@2D node path) was the last elementwise kernel still on the
plain scalar `s += a[i,k]*b[k,j]` order. The user started a SIMD rewrite to
sweep the **output column axis** — the one axis that is contiguous in a
row-major `B` — leaving only the contraction strided. This session finished,
corrected, and validated it, and measured whether it actually pays off.

## What changed

`src/shinro/runtime/linalg.zig` — `matmul(m, k, n, a, b)` gained a vector route:

- Scalar route when `SIMD_VL <= 1 or n < SIMD_VL` (unchanged arithmetic, so the
  small/classical shapes stay on the exact scalar order on every target).
- SIMD route: broadcast `a[i][p]` (a free scalar broadcast on NEON/AVX) and
  accumulate `@mulAdd` into a `@Vector(SIMD_VL, f64)` over `b[p*n + j0 ..]`.
  Each lane sums `p` in the same serial order as the scalar loop, so **no
  reassociation** is introduced — only the mul+add fusion differs (same
  property as the existing `dot`).
- Scalar tail for the `n % SIMD_VL` columns.

`src/shinro/runtime/tests/linalg.zig` — added `matmul` with `n = 19`
(whole-vector sweep + tail) against a scalar reference. All existing cases have
`n ∈ {2,3,4} < SIMD_VL`, so none of them reached the vector path.

## Corrections made in review

The WIP (committed by the external turn-end harness as `133492e`) did not
compile and had a latent shape bug:

1. `out[i*n+j0..][0..SIMD_VL].*=acc;` sat **outside** the `while` loop, so
   `acc` was out of scope (`error: use of undeclared identifier 'acc'`) — and
   even hoisted, a single post-loop store can only keep the last vector, dropping
   every earlier one for `n > SIMD_VL`. The store moved inside the loop.
2. `b[p*n+j0][0..SIMD_VL]` sliced a scalar `f64`; needs `b[p*n+j0..][0..SIMD_VL]`.
3. The guard used `SIMD_MIN_K` (the **dot-product contraction** threshold, ≥8)
   as an output-column threshold. Not a correctness bug (`SIMD_MIN_K ≥ SIMD_VL`,
   so no overrun) but the wrong constant's meaning, and it forced every `n < 8`
   scalar. The real requirement is `n >= SIMD_VL` (below it `n_full == 0` and the
   vector store would run past a row). Guard became `SIMD_VL <= 1 or n < SIMD_VL`;
   `SIMD_VL < 1` was dead since `SIMD_VL = … orelse 1`.
4. The tail store was inside the `p` loop in the earlier revision (k redundant
   writes); the later revision emptied the tail loop entirely. Restored a correct
   tail.

## Benchmarks (x86-64 AVX, `SIMD_VL = 4`, ReleaseFast, per call, volatile anti-hoist)

| shape (m×k×n) | scalar | SIMD | speedup |
|---|---:|---:|---:|
| 3×3×3 | 3.3 ns | 3.2 ns | 1.00x (n<4 → scalar) |
| 4×4×1 | 3.3 ns | 3.2 ns | 1.00x (n<4 → scalar) |
| 12×12×4 | 56.3 ns | 27.9 ns | **2.0x** |
| 1×128×128 | 12.4 µs | 2.89 µs | **4.3x** |
| 1×256×128 | 25.9 µs | 6.41 µs | **4.0x** |
| 128×128×128 | 1.65 ms | 374 µs | **4.4x** |
| 1×512×512 | 297 µs | 88.7 µs | **3.3x** |

The vector route lands at the `≈VL×` ceiling, i.e. compute-bound matmuls get
full-width FMA. Payoff is **shape-conditional**: it engages only for `n ≥ SIMD_VL`.
On the x86 dev host the shipped classical graphs (`n ∈ {1,3}`) stay scalar; on
the **Pi** (NEON `SIMD_VL = 2`) `n = 3` does take the vector path, so the win is
larger on the deployment target. The policy hot path remains `gemm`/`dot`
(already vectorized over the contraction); `.matmul` is the non-transposed 2D
classical path.

## Follow-up: shared row sweep, `vecmat` gets the same treatment

`vecmat` (1D @ 2D → `n`) is exactly the `m = 1` case of the column sweep, so
rather than duplicate the SIMD block it was factored into a private
`rowMatVec(k, n, a_row, b, out)` helper that both kernels call: `matmul` once per
output row, `vecmat` for its single row. `matmul` became a loop over
`rowMatVec`; the guard, the vector store, and the tail live in exactly one place
now.

This also fixes the same latent blind spot on the `vecmat` side (the only test
was `k=3, n=4`, and on x86 `n=4 ≥ VL` was the sole case that reached vector code).
Added a `k=5, n=19` case (vector sweep + tail) against a scalar reference.

- Prototyping gotcha: `lower.zig`'s `@import("qp.zig")` is resolved **even when

  the `solver_meta` anonymous import is). `qp.zig` sits next to `lower.zig`, so
  the test module finds it — but the test module must stay rooted at
  `lower.zig` for that relative import to resolve. No OSQP bake is needed.

## Split the C-ABI export out of `lower.zig` into `entry.zig`

### Why

`lower.zig` conflated three concerns: the VM, the graph binding
(`@import("graph_data")` + `solver_meta`/`qp`), and the C-ABI surface
(`export fn shinro_step`). That coupling is what forced a graph fixture to be
wired into the *module* for every test graph. Separating the binding/export
from the VM lets the VM take the graph as a comptime parameter
(`Vm(Ctx)`), so tests — and, later, a multi-graph fixture table — inject their
own graph with no per-graph anonymous-import choreography.

### What changed

- `src/shinro/runtime/lower.zig` — now graph-agnostic: `pub fn Vm(comptime Ctx:
  type) type` wraps the whole VM (`workspace`, `step`, and the four helpers) in
  a container, with `const g = Ctx.graph;` aliasing the injected graph so the
  **body is byte-for-byte unchanged** (every `g.nodes` / `g.offsets` reference
  stands). The `graph_data`/`solver_meta`/`qp` imports and the `export fn` are
  gone; `sm`/`qp` now come from `Ctx` (only referenced for QP graphs).
- `src/shinro/runtime/entry.zig` (new) — the deployment entry: the only file
  that imports `graph_data` (plus `solver_meta`/`qp.zig` when QP), assembles
  `Ctx`, and declares `pub export fn shinro_step` forwarding to
  `lower.Vm(Ctx).step`.
- `src/shinro/runtime/build.zig` — lib module root `lower.zig` → `entry.zig`;
  the VM test module is now an anonymous-import-free `vm_mod`, and the fixture
  graph is wired to the *driver* (`tests/lower.zig`) instead.
- `src/shinro/runtime/tests/lower.zig` — binds the fixture itself
  (`const Ctx = struct { pub const graph = g; … }`) and calls
  `lower.Vm(Ctx).step`.
- `src/shinro/runtime/README.md` + `docs/codegen.md` — table/narrative rows for
  `entry.zig` and the graph-agnostic VM.

### Verification

- `zig build test`: **51/51 passed** (48 linalg + 1 emosqp + 2 VM).
- `make test-zig` (real ReleaseFast `.so` + ctypes oracle + pytest): **91
  passed, 2 skipped** — the shipped KF+LQR oracle, the MPC/`.solve_qp` oracle,
  and the ONNX/recurrent oracles all still match `interpret()`, so the QP path
  through `entry.zig`'s conditional `solver_meta`/`qp` wiring is intact.
- Binary check: built pre-refactor HEAD in a scratch worktree and diffed the

The real policies lower to big *Zig source* because the f32 weight blob is
written as hex literals: go2 4.1 MB, drone_gru 1.9 MB. A raw f32 `.bin` +
`@embedFile` cuts them to 736 KB / 342 KB — ~1.2 MB for all four fixtures vs
~6 MB. Compile time was never the issue (go2 builds in ~1.7 s); repo size was.

### Quadrotor plant: standalone 12-state dynamics

**What.** Turned the `Quadrotor` placeholder into a working standalone plant.
HEAD `ba22350` ("added rotation and transformation matrices") had already
swapped in a partial `__init__` + the rotation/T helpers, but dropped the frozen
`Config`, the abstract methods, and `from_config` — so `import shinro` was
failing with `TypeError: Plant 'Quadrotor' ... does not define a frozen Config
dataclass`. This entry restores the contract and fills in the dynamics.

**State/control contract.** 12 states
`[x, y, z, roll, pitch, yaw, vx, vy, vz, p, q, r]` — position, Euler angles,
world-frame linear velocity, and **body angular rates**. 4 controls = the four
rotor angular speeds `[w1, w2, w3, w4]`. The sample TOML comment used to
advertise `[thrust, tx, ty, tz]`; updated to the rotor-speed contract. `+`
rotor layout (1/3 CCW along ±x, 2/4 CW along ±y):

```
F     = k * sum(wi^2)
tau_x = k*l*(w2^2 - w4^2)      tau_y = k*l*(w3^2 - w1^2)
tau_z = b*(w2^2 + w4^2 - w1^2 - w3^2)
```

Translation applies body thrust along body `+z` through `R = Rz(psi) Ry(theta)
Rx(phi)` and cancels gravity. Rotation is Euler's rigid-body equation
`w_dot = I^-1 (tau - w x (I w))` (gyroscopic term included) with Euler
kinematics `eta_dot = T(phi, theta) w`.

**Design decisions.**

- `dynamics` is **batch-capable** and backend-routed (column idiom), so the same
  function backs `step`, finite-difference `get_model`, and MPPI lowering. The
  `R` and `T` matrices are expanded into **closed-form components** rather than
  applied as 3x3 products — on the batched path a matrix would be rank-3
  `(N, 3, 3)`, which the graph backend (strictly 2-D) does not represent. Traced
  cleanly: 133 nodes, no new VM ops.
- Hit the Tracer quirk that it has **no reflected division**
  (`1.0 / cos(pitch)` raises `TypeError`): rewritten as
  `(q sin(phi) + r cos(phi)) / cos(theta)`.
- `get_model()` defaults `u0` to the **hover rotor speed** `sqrt(m g / 4k)`, not
  zeros. Rotor forces are quadratic in speed, so `u0 = 0` gives `B = 0` and a
  useless linearization. At hover `B` is nonzero only in row 8 (collective
  thrust -> z) and rows 9-11 (rotor differences -> body torques).
- `get_model()` defaults `x0` to the level, zero-velocity state; together with
  the hover `u0` this is the true hover equilibrium.
- MuJoCo engine mode is still TODO: `physics_engine` stores the engine and
  inherits its backend, but `step` raises `NotImplementedError` while an engine
  is attached rather than silently integrating past it.
- Optional `state_bounds`, matching the other analytical plants.

**Verification.** `tests/test_plants.py::TestQuadrotor` (20 tests, each run
against numpy and torch via the `bk` fixture) plus `Quadrotor` added to
`TestBatchCapableDynamics`'s plant table (`n_x = 12`, `n_u = 4`): hover fixed
point, thrust direction and Euler-rate map checked against the `_rotation_matrix`
/ `_angular_transformation_matrix` references, rotor torques, gyroscopic
coupling, batch/single agreement, hover input-Jacobian structure, `from_config`,
and validation.

### Quadrotor: configurable rotor mixer

Follow-up to the entry above, prompted by a question about whether the torque
pairings were "flipped". They were not — the pairing is fixed by *where* rotors
1-4 sit (a rotor on the x-axis can only make pitch; a rotor on the y-axis can
only make roll), and the class docstring pinned that layout. The real fix was to
make the layout data instead of hardcoding one numbering.

- Added `RotorConfig` (`x`, `y`, `spin`) and an optional `[[rotors]]` table on
  `QuadrotorConfig`. `Quadrotor.__init__` takes `rotors=[(x, y, spin), ...]`;
  when omitted it builds the same default `+` layout from `radius`.
- The rotor mix is now a general mixer over the table:
  `F = k*sum(w_i^2)`, `tau_x = k*sum(y_i w_i^2)`,
  `tau_y = -k*sum(x_i w_i^2)`, `tau_z = -b*sum(sigma_i w_i^2)`. For the default
  table this reduces exactly to the previous closed forms (verified bit-for-bit
  in the existing tests). It stays a **Python-level unroll** over the static
  table, so it is still trace-safe (169 graph nodes vs 133 before) — no new ops,
  no `(N,3,3)` matrices.
- So any numbering/placement — `+`, `X`, or the "1/3 lateral, 2/4 fore/aft"
  variant from the question — is now just a different table. The alternative
  numbering is the commented example in `samples/plants/quadrotor.toml`.
- Tests: default table is the `+` layout; a custom table moves roll to (1,3) and
  pitch to (2,4); `from_config` parses `[[rotors]]`; a 3-rotor table raises.
  `pytest test_plants/test_factories/test_linearization/test_batched_adapter`
  -> **270 passed, 1 skipped**; `ruff` + `pyrefly` clean.

### Quadrotor multi-surface SMC demo

Added `demos/demo_quadrotor_smc.py` (`python -m demos.demo_quadrotor_smc`),
answering the "can we stack surfaces?" question with a working closed loop.

- Single-surface SMC cannot stabilize the 12-state / 4-input quadrotor: `s = cᵀx`
  is scalar, so one equation against four rotors is underdetermined. Stacking
  one surface per input-matched DOF (altitude + roll/pitch/yaw) makes `C` a
  `(4, 12)` matrix; `C g` is then a square **decoupling matrix** (near hover,
  the rotor mixer: thrust + the three torques), so
  `u = u_trim + (C g)^-1 (s_dot_want - C f)` is fully determined.
- The demo closes the loop on the framework `Quadrotor` plant with the host
  supplying `f` (nonlinear drift) and `g` (`linearize_plant` control
  effectiveness at the hover trim): from `[z=0.3, roll=0.15, pitch=-0.12,
  yaw=0.08]` it converges to `z 2.5e-4`, roll/pitch/yaw ~1e-4, and thrust
  `4.9051 N` == weight. x/y drift (unactuated — a position loop cascades onto
  the roll/pitch setpoints).
- Contrast sections: the single-surface framework `SlidingModeController` on the
  same 12-state surface drifts away (z -> 58); and `det(C g)` collapses to 0 for
  stopped rotors or pitch = 90 deg (gimbal lock), motivating the `healthy`
  fail-safe (command zero + flag, never a raise — a Zig panic across the C ABI
  aborts the host).
- The demo implements the multi-surface law inline; generalizing
  `SlidingModeController` to a surface matrix `C` (reusing the existing
  `inv`/`solve` op, plus a rank guard) is the framework path if it should be
  lowered/deployed.
