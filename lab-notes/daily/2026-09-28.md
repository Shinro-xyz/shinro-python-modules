# 2026-09-28 — SIMD column-sweep `matmul` + wide-n coverage

Branch: `main`

## Why

`matmul` (the 2D@2D node path) was the last elementwise kernel still on the
plain scalar `s += a[i,k]*b[k,j]` order. The user started a SIMD rewrite to
sweep the **output column axis** — the one axis that is contiguous in a
row-major `B` — leaving only the contraction strided. This session finished,
corrected, and validated it, and measured whether it actually pays off.

## What changed

`src/shinro/runtime/linalg.zig` — `matmul(m, k, n, a, b)` gained a vector route:

- Scalar route when `SIMD_VL <= 1 or n < SIMD_VL` (unchanged arithmetic, so the
  small/classical shapes stay on the exact scalar order on every target).
- SIMD route: broadcast `a[i][p]` (a free scalar broadcast on NEON/AVX) and
  accumulate `@mulAdd` into a `@Vector(SIMD_VL, f64)` over `b[p*n + j0 ..]`.
  Each lane sums `p` in the same serial order as the scalar loop, so **no
  reassociation** is introduced — only the mul+add fusion differs (same
  property as the existing `dot`).
- Scalar tail for the `n % SIMD_VL` columns.

`src/shinro/runtime/tests/linalg.zig` — added `matmul` with `n = 19`
(whole-vector sweep + tail) against a scalar reference. All existing cases have
`n ∈ {2,3,4} < SIMD_VL`, so none of them reached the vector path.

## Corrections made in review

The WIP (committed by the external turn-end harness as `133492e`) did not
compile and had a latent shape bug:

1. `out[i*n+j0..][0..SIMD_VL].*=acc;` sat **outside** the `while` loop, so
   `acc` was out of scope (`error: use of undeclared identifier 'acc'`) — and
   even hoisted, a single post-loop store can only keep the last vector, dropping
   every earlier one for `n > SIMD_VL`. The store moved inside the loop.
2. `b[p*n+j0][0..SIMD_VL]` sliced a scalar `f64`; needs `b[p*n+j0..][0..SIMD_VL]`.
3. The guard used `SIMD_MIN_K` (the **dot-product contraction** threshold, ≥8)
   as an output-column threshold. Not a correctness bug (`SIMD_MIN_K ≥ SIMD_VL`,
   so no overrun) but the wrong constant's meaning, and it forced every `n < 8`
   scalar. The real requirement is `n >= SIMD_VL` (below it `n_full == 0` and the
   vector store would run past a row). Guard became `SIMD_VL <= 1 or n < SIMD_VL`;
   `SIMD_VL < 1` was dead since `SIMD_VL = … orelse 1`.
4. The tail store was inside the `p` loop in the earlier revision (k redundant
   writes); the later revision emptied the tail loop entirely. Restored a correct
   tail.

## Benchmarks (x86-64 AVX, `SIMD_VL = 4`, ReleaseFast, per call, volatile anti-hoist)

| shape (m×k×n) | scalar | SIMD | speedup |
|---|---:|---:|---:|
| 3×3×3 | 3.3 ns | 3.2 ns | 1.00x (n<4 → scalar) |
| 4×4×1 | 3.3 ns | 3.2 ns | 1.00x (n<4 → scalar) |
| 12×12×4 | 56.3 ns | 27.9 ns | **2.0x** |
| 1×128×128 | 12.4 µs | 2.89 µs | **4.3x** |
| 1×256×128 | 25.9 µs | 6.41 µs | **4.0x** |
| 128×128×128 | 1.65 ms | 374 µs | **4.4x** |
| 1×512×512 | 297 µs | 88.7 µs | **3.3x** |

The vector route lands at the `≈VL×` ceiling, i.e. compute-bound matmuls get
full-width FMA. Payoff is **shape-conditional**: it engages only for `n ≥ SIMD_VL`.
On the x86 dev host the shipped classical graphs (`n ∈ {1,3}`) stay scalar; on
the **Pi** (NEON `SIMD_VL = 2`) `n = 3` does take the vector path, so the win is
larger on the deployment target. The policy hot path remains `gemm`/`dot`
(already vectorized over the contraction); `.matmul` is the non-transposed 2D
classical path.
