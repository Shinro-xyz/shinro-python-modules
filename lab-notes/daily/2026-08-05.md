### 2026-08-06 00:07 UTC — MPPI brought to codebase standard

**What changed**

`src/shinro/controllers/mppi.py` was a raw numpy script: `MPPI_Controller`
snake-case class, no `ArrayBackend`, no registry decorator, no `from_config`,
no docstrings, no tests, `reset()` a no-op `pass`. Brought it up to the
standard set by `LQR`/`MPC_LTI`/`SlidingModeController`:

- **Renamed** `MPPI_Controller` → `MPPIController` (PascalCase, matches
  `PIDController`/`SlidingModeController`), registered as `"MPPI"` via
  `@register_controller`.
- **`ArrayBackend` support**: constructor takes `backend: ArrayBackend | None
  = None`; `compute()` bridges the state in with `bk.to_numpy` and the action
  out with `bk.from_numpy`. The sampling/rollout/softmax loop stays numpy
  (torch has no `np.random.normal` equivalent) — same precedent as `MPC_LTI`
  bridging to OSQP and `LQR` bridging to scipy DARE.
- **`seed` param** — `np.random.default_rng(seed)` for reproducible sampling
  (the raw script used the global `np.random`).
- **`reset()`** now zeros the nominal control sequence and clears
  `_last_epsilon`/`_last_costs` bookkeeping.
- **`from_config`** — builds the controller from a TOML dict; `dynamics_fn` /
  `cost_fn` are callables that can't live in TOML, so they're left `None` and
  injected after construction (`ctrl.dynamics_fn = ...`), per user decision.
  `compute()` raises a clear `RuntimeError` if they're unset.
- **Guarded the K=1 shift** — `self.u[-1] = self.u[-2]` was an `IndexError`
  for a horizon of one; only shift when `K > 1`.
- **Full Sphinx docstrings** — module, class, methods, `Args:`/`Returns:`/
  `Config fields:`/`Raises:` blocks matching codebase convention.
- **Exported** `MPPIController` from `controllers/__init__.py` (+ docstring
  list + `__all__`) and added `configs/controllers/mppi.toml`. (These two were
  already committed on this branch in `93ed7e3`.)
- **Preserved** the existing control-penalty formula `lam * sum(u/σ² * ε)`
  (not the textbook `λ/2` factor) per user decision; the math-accuracy tests
  pin *that* formula.

**Tests** (`TestMPPI` in `tests/test_controllers.py`, 13 tests × numpy/torch):

- Construction validation (bad `num_samples`/`temperature`/`horizon`/`dt`),
  compute shape, requires-callables `RuntimeError`, bounds respected.
- **Mathematical accuracy** (analytic verification, matching the
  `TestLQR`/`TestSMC` standard): softmax-weighted perturbation update
  `u_0 = Σ w_i ε_i` with `w_i = softmax(-costs/λ)` computed by hand; the
  control-penalty term reducing to exactly `λ u^T Σ⁻¹ ε` with zero stage cost;
  the receding-horizon shift `u[:-1]=u[1:]`, last duplicated; returned action
  == pre-shift `u[0]`; clamp-before-rollout placement (cost_fn never sees an
  out-of-bounds `u`).
- Behavior: regulation to zero on a first-order integrator plant, `reset()`
  clears state, `from_config`, seed reproducibility, torch-backend bridging.

**Test results**

- `make test-controllers`: 121 passed, 1 skipped (torch-only test skipped on
  numpy param).
- `make test`: 734 passed, 1 skipped, 33 deselected, 37 errors — the 37 MCP
  functional errors are pre-existing (identical count on the stashed baseline).
- `ruff check .` clean; `pyright` on `mppi.py`: 0 errors.

### 2026-08-06 00:51 UTC — BatchedDynamicsAdapter + MPPI batched rollout, first-class in the scenario pipeline

Phase 1 of the Isaac-Lab-style batching story. A codebase audit confirmed that
no plant or controller handled a leading batch dimension `(N, D)` — every
per-step method assumed 1D state/control, and `InvertedPendulum`/`CartPole`
used the `bk.array([indexed_scalar, ...])` reconstruction pattern that
destroys any batch dim. This pass delivers batched ops specifically for MPPI's
N-rollout loop (the one controller where the batch dim lives *inside* a single
`compute()` call), via a reusable adapter. Phase 2 (parallel environments,
`reset(env_ids)` across all ABCs) is a separate, deferred multi-session
effort.

**What changed**

- **`utils/array_backend.py`** — added `stack()` to `ArrayBackend`
  (abstract), `NumpyBackend` (`np.stack`), `TorchBackend` (`torch.stack`).
  This is the primitive the nonlinear plants need for vmap-safe state
  reconstruction.
- **`plants/inverted_pendulum.py`, `plants/cartpole.py`** — `dynamics()`
  now returns `bk.stack([...])` instead of `bk.array([...])` (2 lines each).
  This alone makes those two dynamics vmap-compatible; verified
  `torch.vmap(plant.dynamics)` produces `(N, D)` from `(N, D), (N, D_u)`.
- **`utils/batched_adapter.py` (new)** — `BatchedDynamicsAdapter` wraps a
  `Plant` and exposes batched `dynamics_fn(x[N,Dx], u[N,Du], dt) -> (N,Dx)`
  and `cost_fn(x[N,Dx], u[N,Du], Q, R, x_ref=None) -> (N,)`. Two paths:
  - **LTI** (`get_model()` → A, B): `x @ A.T + u @ B.T` — true batched
    matmul, one native kernel on numpy and torch.
  - **Nonlinear** (`dynamics()` → dx/dt): semi-implicit Euler
    `x + dt*f(x,u)`; on torch auto-vectorized via `torch.vmap`, on numpy a
    Python loop over the batch.
  All ops use the plant's backend, so torch inputs stay torch throughout.
- **`controllers/mppi.py`** — the rollout loop moved from hard-coded numpy
  to `self.bk` ops (batched dynamics/cost execute as backend-native tensor
  ops; the torch backend now genuinely runs the rollout, not just bridges
  I/O). RNG sampling + softmax stay numpy, bridged per-step via
  `bk.from_numpy` (same pattern as MPC→OSQP). New `attach_plant(plant,
  Q=None, R=None)` wires the adapter in (Q/R default to the config's
  `state_cost`/`control_cost`, else identity); `compute(x0, x_ref=None)`
  supports trajectory tracking via the reference-shifted cost.
- **`factories/scenario_factory.py`** — after building plant + controller,
  `if isinstance(controller, MPPIController): controller.attach_plant(plant)`
  (runs before `_validate_dimensions` so MPPI's `D_u` is set for the check;
  a new `D_u`-based validation catches control-dim mismatches). Also fixed a
  pre-existing bug: `resolve_config_path` crashed on `PosixPath` input
  (`path.startswith` on a non-str), which blocked every scenario build —
  now coerces to `str` first.
- **`tests/integration/helpers/scenario_runner.py`** — `_compute_control`
  dispatch gets an MPPI branch: `ctrl.compute(estimate, x_ref=reference)`.
- **`configs/controllers/mppi_base.toml` (new)** + **`tests/integration/
  scenarios/mppi_base_tracking.toml` (new)** + **`tests/integration/
  test_mppi_tracking.py` (new)** — full closed loop MPPI→Kalman→base→MuJoCo.
- **`Makefile`** — added `test-batched-adapter` target (per-module convention,
  like `test-controllers`/`test-array-backend`) and included
  `tests/test_batched_adapter.py` in `test-quick` so the adapter unit tests
  run in the fast suite (they were already picked up by the directory-wide
  `make test`).

**Key decisions**

- Phase 1 scope only: no `reset(env_ids)`, no batched compute for LQR/PID/
  MPC/SMC (single-state is correct for them). The adapter's public interface
  (`dynamics_fn`/`cost_fn`) matches the future batched-first contract so the
  work carries forward to Phase 2.
- Nonlinear plants + torch use `vmap`; if that ever proves fragile, the
  numpy loop fallback is correctness-preserving (just not batched).
- `ArmRobot` via adapter uses its approximate LTI model (`A=I₆, B=dt·I₆`),

### 2026-08-06 01:30 UTC — MPPI: hoist loop-invariant CPU→GPU transfers out of the rollout loop

**What changed**

`MPPIController.compute()` had two `bk.from_numpy` calls *inside* the K-step
rollout loop (the control-penalty term). On a torch backend each `from_numpy`
is a CPU→GPU transfer with a sync point, so a K=15 horizon did 30 uploads per
`compute()` call — 15 of a `(D_u,)` array and 15 of an `(N, D_u)` epsilon
slice, even though all three inputs (`epsilon`, `self.u`, `noise_sigma²`) are
loop-invariant.

Hoisted the three conversions out of the loop:

```python
eps_b = self.bk.from_numpy(epsilon)              # (N, K, D_u) — once
u_nom_b = self.bk.from_numpy(self.u)             # (K, D_u) — once
sigma2_b = self.bk.from_numpy(self.noise_sigma**2)  # (D_u,) — once
```

The loop body now indexes the pre-converted tensors (`u_nom_b[k] / sigma2_b`,
`eps_b[:, k, :]`) and is fully backend-resident — zero transfers inside the
K-step loop. The math is identical; only *when* the arrays are converted
changed. Updated the surrounding comment to reflect "bridged once before the
loop" instead of "per step."

**Key decisions**

- Kept the K-step Python loop rather than vectorizing over time (lifted-matmul
  / parallel-scan). The loop is already GPU-resident after this fix; the
  remaining K kernel launches (~10 µs each) are negligible against a 20 ms
  control budget, and the lifted-matmul alternative costs O(K²) memory for a
  sub-microsecond gain at typical horizons (K=10–30). Classic YAGNI.
- The fundamental numpy↔torch bridge (RNG sampling + softmax stay numpy, no
  RNG in `ArrayBackend`) is unchanged and documented — same pattern as
  MPC→OSQP.

**Test results**

- `make test-controllers`: 130 passed, 2 skipped — the two math-accuracy tests
  that pin the control-penalty formula (`test_mppi_control_penalty_term`,
  `test_mppi_softmax_weights_analytical`) pass under both numpy and torch,
  confirming the refactor is value-identical.
- `ruff check` clean; `pyright` on `mppi.py`: 0 errors.

**Files touched**

`src/shinro/controllers/mppi.py`.
