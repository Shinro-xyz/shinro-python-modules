# 2026-10-13 — LTISystemsAnalyzer robustness: stability gate + list coercion

Branch: `main`

## Why

The LTI analyzer (`src/shinro/utils/controllability_checker.py`) is a public
utility exposed through the MCP server, and it had two defects that turned a
diagnostic tool into a crash:

1. **`summary()` raised on an unstable-but-controllable system.** It gated the
   Gramian sections on `is_controllable()` / `is_observable()` — *rank* tests —
   while `controllability_gramian()` requires *stability* (Hurwitz A). An
   unstable A such as `[[0,1],[1,0]]` (eigenvalues ±1) is rank-controllable, so
   `summary()` reached the infinite-horizon Gramian and raised
   `ValueError: A is not Hurwitz`. The `*not defined* (unstable A)` branches
   already existed in `summary()` — the gate made them unreachable. The
   trailing unconditional `hankel_singular_values()` would have crashed the same
   way.
2. **Raw list matrices crashed later.** The constructor used `A.shape[0]`
   directly, so `A=[[0,1],[-1,-2]]` raised
   `AttributeError: 'list' object has no attribute 'shape'` before any analysis.

This was picked up while surveying non-component work; the only open issue
(#18) is a pure component backlog, so analyzer robustness was untracked.

## Change

`src/shinro/utils/controllability_checker.py`:

- Added **`_is_hurwitz()`** (every eigenvalue has strictly negative real part).
  `summary()` now gates the controllability/observability Gramians on stability,
  not rank, so an unstable system reports `*not defined* (unstable A)` instead of
  raising; the Hankel section is emitted only when both Gramians exist.
- The duplicated inline eigenvalue checks in `controllability_gramian()` and
  `observability_gramian()` now call `_is_hurwitz()` (behaviour-preserving).
- Added **`_coerce()`** — converts Python `list`/`tuple` to a backend array and
  passes arrays and sparse matrices through unchanged; applied to A/B/C/D in
  `__init__`. Constructor signature widened to a new `MatrixLike` alias
  (`np.ndarray | list | sparray | spmatrix`) so the accepted forms are truthful.

Tests:

- `tests/test_controllability_checker.py` — new `TestSummaryRobustness` (unstable
  `summary()` does not raise and reports undefined Gramians; stable system still
  gets the Hankel section; `_is_hurwitz` matches eigenvalue signs) and
  `TestListInputCoercion` (list matrices accepted; list and array inputs give an
  identical Gramian and `rank_report`).
- `tests/test_adversarial.py` — `test_summary_on_zero_system` **asserted the crash
  as intended behaviour** (`pytest.raises(ValueError)`). Rewritten to pin the
  corrected behaviour. Worth recording: the old test encoded the bug as the
  spec, which is why it survived.

## Follow-up — MPC_DeltaU returns the applied control, not the increment

**The bug.** `MPC_LTI_DeltaU.compute()` solved the augmented QP — whose control
variable is the *rate* `Δu` — and returned the bare `z_opt[0:m]` increment. But
the framework's uniform contract is that a controller's output **is the applied
control**: `runner.py` does `control = clip(ctrl.compute(...))` → `plant.step`
and then `u_prev = control`, and `compose.py` wires both `u` and `state_u_prev`
to the same returned value. So the plant received `Δu` each tick instead of the
accumulated `u = u_prev + Δu`, and `u_prev` fed back the last increment rather
than the last applied control. The controller's own augmented model
(`z_{k+1} = [A B; 0 I] z_k + [B; I] Δu`) assumes the plant is driven by
`u_prev + Δu`, so its prediction was systematically off by `u_prev`.

**Why no test caught it.** Every existing MPC_DeltaU check pins shape/finiteness
or *live-vs-traced parity* (`np.allclose(traced["u"], u_np)`), and both sides
call the same controller — a self-consistency oracle cannot see a wrong
contract. The closed-loop `.so` oracle and `compose` parity test both thread the
returned value as `u_prev`, so they agree with each other while both are wrong.

**Evidence.** Pre-fix, `compute(x=0, u_prev=2.0)` returned `-1.18` (an
increment); with a large `delta_u_penalty` forcing `Δu→0` it returned `~0`
instead of `~u_prev`. Post-fix it returns `0.8204 = 2 + Δu`, and the large-`S`
case returns `0.299997 ≈ u_prev`.

**Fix** (`src/shinro/controllers/mpc_lti.py`): return `u_prev + Δu` from
`compute`, and document that the returned value is the applied control.
`Tracer.__add__` exists (`codegen/tracing.py`), so the accumulation traces as an
`add` node — no new op or lowerer change.

**Test** (`tests/test_controllers.py`): `test_mpc_lti_deltau_returns_accumulated_control`
— huge `delta_u_penalty` at zero state error ⇒ the returned control must stay
near `u_prev` (the bare increment would be ~0).

**Verification:** `make lint` clean (pyrefly 0 errors); `make test` **2005 passed
/ 5 skipped**; `tests/test_zig_lowering.py` full **97 passed / 2 skipped**,
including `test_so_matches_live_components[kf_mpc_deltau]` (compiled `.so` vs
live) and the manifest test. `graph_data_manifest.json` clobbered by the suite
and restored.

## Follow-up — plant model terms at an operating point (SMC `g(x, u)`)

**The bug.** The SMC model pair `f_x`/`g_x` was evaluated at zero control in
*both* the codegen (`build._trace_plant_model`) and gate A
(`gate_a._controller_kwargs`): `dynamics(x, 0)` / `control_matrix(x, 0)`. That is
the drift convention and is exact for control-affine plants (force/torque in
`u`). A rotor plant is *not* control-affine in its input — thrust ~ `ω²` — so
`g(x, 0) = 0`, and in fact `control_matrix(x, 0.0)` on the 4-input quadrotor does
not merely return zero: the scalar-0 probe cannot size a 4-wide finite
difference and **errors** (`stack: all input arrays must have the same shape`).
Any rotor-plant SMC therefore tripped the controllability guard (fail-safe
`healthy=0`, zero command) — or worse, could not be formed at all.

**Fix — one site, both paths.** `Plant.model_terms(state, bk=None, n_u=None)`
now returns the control-affine pair at the plant's operating point:
`g_x = ∂f/∂u|_(x,u_op)`, `f_x = f(x, u_op) − g_x·u_op` (the tangent line, so
`f_x + g_x·u` reproduces the true `f(x, u_op)` at `u = u_op`). The operating
control comes from a new `Plant.operating_control()` (default `None` = zero).
`build._trace_plant_model` and `gate_a._controller_kwargs` both call
`model_terms`, so the live and lowered models cannot drift.

- Control-affine plants: `operating_control()` is `None` → `f(x,0)` / `g(x,0)`,
  **bit-identical** to before (the shipped SMC pendulum graph and gate A are
  unchanged).
- `Quadrotor.operating_control()` returns hover rotor speeds `√(mg/4k)`;
  `get_model()` now reuses it (same value, one definition).

**Measured.** Pendulum: `model_terms == (dynamics(x,0), control_matrix(x,0))`
exactly, and traced == live. Quadrotor: `operating_control = [1.10736]×4`;
`g(x, hover)` is `(12, 4)`, `|g| = 99.44`; `f_x + g_x·u_op == dynamics(x, u_op)`
exactly; traced == live.

**Tests** (`tests/test_plants.py::TestModelTerms`, ×numpy/torch):
`operating_control()` defaults to `None`; affine plants reduce to the drift
convention; the quadrotor trims at hover; the quadrotor model is the tangent at
`u_op` with `|g| > 1`; `_trace_plant_model` matches the eager pair.

**Verification:** `make lint` clean (pyrefly 0 errors); `make test` **2014 passed
/ 5 skipped**; `tests/test_zig_lowering.py` **97 passed / 2 skipped**. The
existing SMC pendulum compile scenario + gate A pass unchanged.
`graph_data_manifest.json` clobbered by the suite and restored.

**Still open (item 2):** the live runner still rejects SMC, so this makes the
compiled rotor path correct but does not yet make SMC scenario-runnable.

## Follow-up — SMC is scenario-runnable (item 2)

**The gap.** `iter_scenario` hard-rejected SMC
(`NotImplementedError("SMC requires f_x/g_x dynamics — not scenario-runnable")`)
and `_compute_control` only knew the `compute(state, reference[, u_prev=...])`
form. SMC's `compute(x, f_x, g_x)` had no path, so the model-input controller
worked only when compiled, never in the live loop.

**Fix — one role dispatcher.** New public
`compose.controller_input_kwargs(input_names, x_hat, x_ref, u_prev, plant,
host_values)`, the live mirror of compose's `_CONTROLLER_INPUT_ROLES` wiring:
`state` (the estimate, or the tracking error `x_hat - x_ref` for a regulator
with no reference input), `reference`, `u_prev`, `model` (the plant pair via
`Plant.model_terms`, at the operating point), and any other name — a free host
input, from `host_values` or left `None` (so eager MPPI samples its own epsilon).
`gate_a` now delegates to it (its private `_controller_kwargs` is gone), and the
runner builds kwargs by role and calls `ctrl.compute(**kwargs)`. Live and
lowered now drive a controller through the same mapping.

The SMC rejection and the runner-local `_compute_control` are deleted; the runner
imports `infer_contract` + `controller_input_kwargs` instead of `inspect` +
`SlidingModeController`.

**Measured.** The new runnable scenario
(`tests/fixtures/scenarios/smc_pendulum_run.toml`, SMC + Kalman on
InvertedPendulum) regulates `|θ|` 0.2001 → 0.0079 rad over 800 steps, finite,
`max|u| = 0.109`.

**Tests** (`tests/test_runner_dispatch.py`): the SMC live scenario regulates and
stays finite/bounded; plus dispatcher units — state role is the error without a
reference, state and reference stay separate when a reference is declared, the
model role uses the plant operating point, a model term with no plant is loud,
and a free host input defaults to `None`.

**Verification:** `make lint` clean (pyrefly 0 errors); `make test` **2021 passed
/ 5 skipped**; `make test-integration` **23 passed** (live LQR/PID/MPC through
the changed dispatcher); `make test-mcp-functional` **37 passed**.
`graph_data_manifest.json` clobbered by the suite and restored.

**Layering note:** `simulation.runner` now imports `codegen.compose` (where the
role map lives; `gate_a` already did). `compose` never imports `simulation`, so
there is no cycle.

## Follow-up — plant-declared nonlinear measurement model (h(x)), live and compiled

**The gap.** Nonlinear estimators had a `measurement_fn` (Python-injectable) and a
linear `measurement_matrix` (`C`), but no way to derive a *nonlinear* `h` from a
scenario/config, and no plant-side sensor model. So a config/scenario-driven
EKF/UKF could only be linear, and the runner fed the estimator `get_state() + noise`
(identity sensor), ignoring any sensor the plant might declare.

**The seam — the plant owns the sensor.** New
`Plant.measurement(state, bk=None)` (default `None`): the true sensor model `h(x)`,
following the same contract as `dynamics` (bk-aware, batch-capable — the EKF
differentiates it with a probe batch, the UKF pushes its sigma batch through it).
`InvertedPendulum.measurement` returns the bob position `[l sinθ, l cosθ]`, a
genuinely nonlinear sensor no `C` can express. Users inherit a plant and override
`measurement` (like `dynamics`/`control_matrix`/`operating_control`).

**Adoption.** `ExtendedKalmanFilter.attach_plant` / `UnscentedKF.attach_plant` now
fill `measurement_fn` from the plant **only when** the filter has neither a
`measurement_fn` nor a linear `C`, and only if the plant actually overrides the
hook (`type(plant).measurement is not Plant.measurement`). Precedence:
`measurement_fn` > `measurement_matrix` > plant `h` > raise. Each side fills
independently (an explicit `dynamics_fn` no longer skips the measurement fill).

**Utilizing it live.** New `StateEstimator.measure(state)` — the estimator's belief
about `h`, used to synthesize the simulated sensor: identity by default, `C @ x`
for KF/Luenberger, `h(x)` for EKF/UKF. The runner now attaches the plant (so a
nonlinear filter adopts `h`) and feeds `_inject_noise(est.measure(true_state))`
instead of `get_state()`. This keeps the sim and the filter consistent **by
construction**: a scenario that models the full state (a KF with `C = I`) is
byte-for-byte unchanged, while an EKF/UKF that adopted the plant's `h` gets the
nonlinear sensor. (Calling `plant.measurement` unconditionally would have broken
`pendulum_balance`, whose KF's `C = I` expects the state, not the bob position.)

**Compiles like any model.** `h` traces inline through the `TraceBackend`, so it
lowers into the kernel (EKF: `h` + its FD Jacobian; UKF: the sigma batch). The
*model* is baked; the *reading* stays the host input port `y`. Tip scenarios:
gate A `0.0`, `sin`/`cos` nodes present, 140/115 nodes.

**Measured.** Runnable `ekf_pendulum_tip_balance.toml`: the reading is the bob
position (`[0.0786, 0.4924]` ≈ `bob(x)+noise`), regulating `|θ| 0.1965 → 0.0018`
with trailing estimate error `0.0061`. Compiled: EKF oracle B `3.1e-15`, UKF oracle
B `4.27e-9`.

**Oracle tolerance.** The UKF tip scenario needs `oracle_tol = 1e-7`: the UKF
*inverts* the measurement covariance `S`, so the VM's `sin`/`cos` differing from
numpy's by <1 ulp is amplified — unlike its linear-`C` scenarios (no transcendentals
in `h`) or the process model (no inversion). The EKF keeps `1e-9` (the FD
amplification, same as its sibling).

**Tests.** Plant `measurement` (value/batch/base-`None`); `attach_plant` fills the
plant sensor, `C`/`measurement_fn` win, a no-sensor plant stays `None`; the
`measure` adapter per filter; gate A for both tip scenarios; the compile gate; and
a live nonlinear-sensor balance scenario.

**Verification:** `make lint` clean (pyrefly 0 errors); `make test` **2045 passed /
5 skipped**; `make test-integration` **24 passed**; `make test-mcp-functional`
**37 passed**. `graph_data_manifest.json` clobbered by the suite and restored.
