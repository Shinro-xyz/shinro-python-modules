# Lab Notes — 2026-09-22

### 2026-09-22 — Fused `gemm` op: ONNX Gemm as one VM kernel

**Why.** NN-based controllers were arriving as ONNX `Gemm` policies, and the
importer decomposed each `Gemm` into `transpose` + `matmul` + `mul` (×2) +
`add`. That chain is correct but expensive in exactly the resource the NN
policy path is constrained by: the VM's `.bss` workspace, sized by
`buf_len = Σ rows*cols`. The `transpose` node alone materializes a full second
copy of every weight matrix in the workspace (for a 512×512 layer, ~2 MiB), on
top of the `cst` slot that already holds it — the 512-wide ONNX benchmarks
carried ~3.6M f64 (28.8 MiB) of buffer for ~1.88M parameters, i.e. roughly
double. A fused dense-layer op removes the transpose and the redundant
`mul`/`add` activation slots, and reads the torch-layout weight by *striding*
instead of moving data.

**Design decisions.**

- **One op, one kernel, one loop.** `linalg.gemm` computes
  `out = alpha*(A@B') + beta*C` for both weight layouts; `transB` flips the
  weight read inside the contraction (`b[j*k+p]` vs `b[p*n+j]`) — the identity
  `(A·Bᵀ)[i,j] = Σ_p A[i,p]·B[j,p]` means the transpose is indexing, never
  data movement. No transpose node, no pre-baked transposed const, no second
  contraction kernel.
- **alpha/beta can't ride in `aux: usize`.** They bake into parallel
  `gemm_alpha`/`gemm_beta` arrays (the `clip_lo`/`clip_hi` pattern), with
  `aux = (table_index << 1) | transB` packing the index and the flag into one
  word. Both are comptime at the read site (`g.gemm_alpha[node.aux / 2]`), so
  they constant-fold in the unrolled node.
- **`transA=1` stays rejected** (loudly, at import). `transA` transposes the
  *activation* — an upstream-layout concern, not a weight-storage artifact;
  and on a 1-D activation it is a numpy no-op. Adding it later is one more aux
  bit.
- **Missing bias → `const(0.0)` scalar.** Keeps the kernel's three-operand
  contract uniform; the zero broadcasts (`c_len == 1`) and annihilates
  `beta*C`.
- **Comptime sizes + vec handling.** `m/k/n` come from the comptime node
  table; a 1-D activation (`vec`) is treated as `m = 1`, so inner layers need no
  reshape glue. Bias broadcast is dispatched on the bias node's flat length
  (`1` → scalar, `n` → row, else full `m*n`).
- Kept the element-loop doctrine: the gemm contraction is a runtime `for` over
  comptime-known bounds; no inline-unrolled element loops.

### 2026-09-22 — Fused `sigmoid` op: ONNX Sigmoid as one VM kernel

**Why.** `Sigmoid` was the last activation still composed in the ONNX
importer: `exp(-x)` → `add` → `div`, i.e. `exp` + `neg` + `add` + `div` plus a
couple of scalar `const`s. The kernel for it already existed in a WIP state in
`linalg.zig`, so the natural move was to finish the six-surface wiring and
route the importer onto it. The fused op is one node, one buffer slot, and
reads the logistic directly instead of materializing `e^{-x}` in the workspace.

**Design decisions.**

- **The negation folds into the exp argument.** `linalg.sigmoid` computes
  `1 / (1 + std.math.exp(-a[i]))` element-by-element, so no intermediate
  `e^{-x}` array exists (unlike a `elementwise_exponential` reuse, which would
  need a scratch buffer). It stays a comptime-sized stack array and a runtime
  element loop, per the element-loop doctrine.
- **WIP kernel was wrong and then invalid.** The original in-progress version
  computed `1/(1+exp(x))` — i.e. `sigmoid(-x)` — and a later edit tried
  `elementwise_exponential(m, -a)`, which is not valid Zig (you cannot negate a
  slice). Replaced with the direct, correct form and a doc comment naming the
  ONNX contract.
- **No attrs, no aux.** Sigmoid is pure elementwise and shape-preserving, so
  the VM op needs no baked tables and `_node_vm_info`'s fall-through
  (`return node.op, 0`) covers it once the enum variant exists.
- **Route the existing decomposition.** `_UNARY_OPS` gains
  `"Sigmoid": "sigmoid"` and `emit_sigmoid` is deleted; the `else` branch
  collapses to an unreachable guard. `add`/`mul` that remain in an imported
  sigmoid policy are the action-space scale/bias baking, not the old chain.

**Files.**

- `src/shinro/runtime/linalg.zig` — corrected/documented `sigmoid` kernel.
- `src/shinro/runtime/lower.zig` — `.sigmoid` VM arm (next to `.relu`).
- `src/shinro/codegen/ops.py` — `@register_op("sigmoid")` numpy oracle.
- `src/shinro/codegen/trace_backend.py` — `TraceBackend.sigmoid` surface.
- `src/shinro/codegen/lower_zig.py` — `sigmoid` appended to the emitted `Op`
  enum.
- `src/shinro/codegen/onnx_import.py` — `Sigmoid` → fused op via `_UNARY_OPS`;
  removed `emit_sigmoid`; docstring updated.
- `src/shinro/runtime/graph_data.zig` — regenerated (`make zig-gen`); only the
  `Op` enum line changes (manifest byte-identical).
- Tests: `src/shinro/runtime/tests/linalg.zig` (hand-computed logistic),
  `tests/test_zig_lowering.py` (sigmoid in `TestLoweredOpsOracle`),
  `tests/test_op_shape_matrix.py` (sigmoid in the pointwise 1-D cells plus a
  2-D cell), `tests/unit/test_onnx_import.py` (asserts the fused op and the
  absence of the old `neg`/`exp`/`div` chain).
- `docs/codegen.md` — added `sigmoid` to both op-vocabulary lists.

**Results.** `make lint` clean; `zig build test` green; targeted run
(onnx + codegen + shape-matrix + zig-lowering) = **200 passed, 2 skipped** (the

### 2026-09-22 — `sigmoid` on the eager backends (ArrayBackend / numpy / torch)

**Why.** The fused `sigmoid` VM op is only reachable through the tracing/ONNX
path. Components call `self.bk.<op>` where the backend is swapped between
eager (`NumpyBackend`/`TorchBackend`) and tracing (`TraceBackend`); `sigmoid`
existed only on `TraceBackend`, so a component written as `self.bk.sigmoid(x)`
would trace to the fused node but crash eagerly on numpy/torch. This closes
that gap so sigmoid is usable backend-agnostically.

**Changes.**

- `src/shinro/utils/array_backend.py` — abstract `sigmoid` on `ArrayBackend`
  next to `tanh`; `NumpyBackend.sigmoid` = `1/(1 + np.exp(-x))` (same
expression as the `ops.py` oracle, for exact parity); `TorchBackend.sigmoid` =
  `torch.sigmoid(x)`.
- `tests/test_array_backend.py` — parametrized `bk` tests (numpy + torch):
  values match the logistic at `[-4..4]`, and large `|x|` saturates to `0/1`
  with no NaN.
- `tests/test_codegen.py` — `TestTraceBackend.test_sigmoid_emits_sigmoid_op`:
  the trace surface records a single `sigmoid` node.

**Results.** `make lint` clean (pyrefly 0 errors over `utils/`);
`tests/test_array_backend.py + tests/test_codegen.py` = **131 passed, 0 skipped**
(torch installed, so both backends ran); full `make test` = **1309 passed,
5 skipped** (was 1304 — the 5 new checks).

**Lint disposition.** pi-lens' `unchecked-throwing-call-python` rule fires on
`out[int(idx)] = 1.0` in both `one_hot` implementations. These lines are
pre-existing and unchanged in behavior (HEAD lines 375/624, shifted to 381/633
by the new methods); the rule flags bare `int()`/`float()` and is documented as
narrow noise in the 2026-09-15 note. Rather than change `one_hot` semantics,
the finding is suppressed at each site with a rule-specific
`# pi-lens-ignore: unchecked-throwing-call-python` comment — `idx` is a numeric
index from upstream `argmax`, not a string parse. The suppression is git-visible
and can be revisited if `one_hot` ever accepts untrusted input.
