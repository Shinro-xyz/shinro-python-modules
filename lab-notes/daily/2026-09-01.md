### 2026-09-01 18:30 UTC — issue #13: lower the 7 host-only ops to Zig

Picked up issue #13 ("Lower the 7 host-only ops to Zig: tanh, relu, exp, argmax, one_hot, slice, copy") and drove it to green. The linalg.zig kernels were already committed earlier today (relu, elementwise_exponential, tanh, argmax, onehot); this session added the VM wiring, emission, and the acceptance oracle.

**Changes:**
- `runtime/lower.zig` — 7 new `switch` arms after `.any`: `.copy`, `.tanh`, `.relu`, `.exp`, `.argmax`, `.one_hot`, `.slice`. Key subtleties:
  - `.argmax` must scan the **input's** flat length (`g.nodes[node.inputs[0]].rows*cols`), not its own (it's a scalar node with rows*cols == 1); index is stored as f64 via `@floatFromInt` since the buffer is all-f64.
  - `.one_hot` reads that float back (`@intFromFloat`) and derives `depth` from `node.rows` (the Python side emits shape `(depth,)` → rows=depth, cols=1). No aux needed.
  - `.slice` uses `node.aux` as the start offset (`out[j] = s[node.aux + j]`); `stop` is implicit in the node's rows*cols.
  - `.copy` is a flat copy — identical to `.reshape`, only present because the Python interpreter needs `.copy()` to break numpy aliasing, which the VM's per-node buffer slots already give you for free.
- `src/shinro/codegen/lower_zig.py` — added the 7 ops to the emitted `Op` enum; added the `slice` → `aux = node.attrs["start"]` branch in `_node_line`.
- `runtime/graph_data.zig` — regenerated (`python scripts/gen_base.py`); base graph unchanged, enum now includes the 7.
- `runtime/tests/linalg.zig` — Zig unit tests for relu/exp/tanh/argmax (incl. tie-break to first)/onehot.
- `tests/test_zig_lowering.py` — refactored the .so build into a reusable `_build_so(composed, build_dir)`; added a `new_ops_so` session fixture building a graph that emits all 7 ops as separate named outputs, and `TestHostOnlyOpsLowering::test_host_only_ops_match_interpreter` comparing .so output to `interpret()` per op across 20 random inputs.

**Bug found along the way:** `lower_zig.py` emitted an invalid `[_]f64{ , };` (leading comma) when a graph had **zero** const nodes — the base_tracking graph always had consts, so this only surfaced with the all-op new-ops test graph. Fixed by guarding the multi-line `const_blob` emission on non-empty.

**Verification:**
- `zig build` (libbase.so) and `zig build test` (7 unit tests) pass.
- `tests/test_zig_lowering.py`: 4/4 pass. Measured the oracle agreement empirically over 200 random inputs:
  - `copy`, `slice`, `relu`, `argmax`, `one_hot`: **bit-exact** (0 ULP).
  - `exp`, `tanh`: exactly **1 ULP** off — both sides wrap the platform libm but round differently in the last bit. The test asserts `rtol/atol=1e-14` for these two, exact for the rest. (True bit-exactness for transcendental would require shipping the same libm algorithm, which is not the point of this issue.)
- Full fast unit gate: **633 passed, 5 skipped**, no regressions.

**Not in scope (orthogonal to #13):** `matrix_power` / `elementwise_exponential` kernels added today are not host-only interpreter ops — `matrix_power` is a backend method that isn't traced/lowered at all. Left as-is for a future slice.

### 2026-09-01 21:30 UTC — OSQP cimport binding works (issue #12 path A)

Got the OSQP C binding compiling, linking, and solving from Zig — the first concrete step toward lowering MPC into the `.so`.

**How the lib was obtained:** the pip `osqp==1.1.3` wheel ships the matching header at `site-packages/osqp/codegen/codegen_src/inc/public/osqp.h` (OSQP C library **1.0.0**), but **no standalone `libosqp.so`** — the C library is statically linked into the Python extension. The `codegen_src` is also a *codegen template*, missing `polish.h`/`amd.h`, so it can't build the full library. Solution: cloned the full OSQP source at the `v1.0.0` tag (with submodules), built `libosqp.so` with cmake, vendored it + the headers into `third_party/osqp/`.

**Changes:**
- `third_party/osqp/` — vendored header (`inc/public`, `inc/private`, cmake-generated `osqp_configure.h`) + built `libosqp.so`.
- `runtime/build.zig` — link `osqp` into `libbase.so`, the test module, and a new standalone `bench` executable. (Zig 0.16 API: `addIncludePath`/`addLibraryPath`/`linkSystemLibrary` are on **Module**, and `linkSystemLibrary` takes an options arg `.{}`.)
- `runtime/tests/osqp.zig` — 3 smoke tests: 2-var box QP (u*=[0,0]), active constraints (u saturates at bound), and a genuinely infeasible problem (non-identity A with conflicting rows → `OSQP_PRIMAL_INFEASIBLE`).
- `runtime/bench/osqp_bench.zig` — standalone benchmark using OSQP's own `info.solve_time`.

**Benchmark (box QP, H=2I, warm-started, OSQP-reported solve_time):**

| n (vars) | MPC equivalent | per-solve |
|----------|----------------|-----------|
| 3 | N=1, n_u=3 | ~7 µs |
| 30 | N=10, n_u=3 (base) | ~20 µs |
| 600 | N=200, n_u=3 (max) | ~300 µs |

**Gotchas hit:**
- `std.debug.print` in a test **corrupts the `zig build test` `--listen` protocol** (silent "failed command" with no error). Fix: benchmark is a separate executable (`zig build bench`), not a test.
- The generated `osqp_configure.h` defines `OSQP_USE_LONG` → `OSQPInt` is `i64`, not `i32`. `@intCast` everywhere handles it.
- OSQP 1.0 status is an **enum starting at 1** (`OSQP_PRIMAL_INFEASIBLE = 3`), not the old 0.6.x `-2`.
- OSQP solves to its **default tolerance (~1e-3)**, not bit-exact — assertions must use ~1e-3, not 1e-9.
- A box-constrained QP with `l ≤ u` is **always feasible** — infeasibility needs a non-identity `A` with conflicting rows. Also `osqp_update_data_vec` rejects `l > u` as invalid data (rc=1).
- `libbase.so` currently has **no runtime `libosqp.so` dependency** (nothing references OSQP symbols yet — the `.solve_qp` op isn't wired). Once it is, the host must find `libosqp.so` (rpath or `LD_LIBRARY_PATH`).
- `*.so` is gitignored, so `third_party/osqp/libosqp.so` won't be committed — a fresh clone needs it rebuilt (or force-added, or the C source compiled in build.zig).

**Next:** wire the real MPC graph (H/F as consts → `q = Fᵀx₀` → `.solve_qp` op → slice `u[:m]`), then explore the codegen path (the pip package ships `codegen_src` specifically for it).

### 2026-09-01 23:00 UTC — OSQP codegen: the no-heap static solver works

Explored the codegen path (issue #12's endgame): generate a **statically-allocated solver** for the MPC problem, compile it into the binary — no malloc, no `libosqp.so` dependency.

**How it works:** `osqp.OSQP().codegen(folder, parameters="vectors")` emits C source (`workspace.c` + `src/*.c` + headers) where the `OSQPSolver solver` global has the problem data (P, A, l, u) **and the pre-factorized KKT matrix** baked in. `parameters="vectors"` = embedded_mode 1, so only q/l/u can be updated at runtime — exactly what MPC needs (only `q = Fᵀx₀` changes per tick). The generated code is self-contained C, compiled into the test via Zig's `addCSourceFiles`.

**Changes:**
- `runtime/codegen/emosqp/` — the generated static solver (from `scripts/gen_emosqp_test.py`).
- `runtime/tests/emosqp.zig` — drives the static solver from Zig: `osqp_update_data_vec(&solver, &q, ...)` → `osqp_solve(&solver)` → read `solver.solution.x`, compared against the Python oracle.
- `scripts/gen_emosqp_test.py` — regenerates both the codegen and the test.
- `runtime/build.zig` — fourth test module compiling the generated C.

**Verification:** `zig build test` → 19/19 pass (14 linalg + 3 osqp binding + 1 cimport MPC QP + 1 codegen static solver). Python oracle 76/76.

**Gotchas hit:**
- `prob.settings.eps_abs = 1e-6` does **not** propagate to the C solver — must use `prob.update_settings(eps_abs=1e-6, ...)` before codegen.
- The terminal control sits in a **flat cost region** (objective diff between two near-optimal solutions ~1e-11), so the codegen solver and a loose-tolerance oracle can differ by ~0.003 on `u_29` while both being optimal. Fix: match the oracle's eps to the codegen's (both 1e-6).
- The generated `emosqp.c` is a demo `main()` — don't compile it; compile `workspace.c` + `src/*.c` only.

**The three paths now all proven:**
| path | heap | dependency | matches Python |
|------|------|-----------|----------------|
| cimport OSQP | one-time malloc | `libosqp.so` | yes (same lib) |
| dense solver (sketched) | none | none | approximate |
| **codegen static solver** | **none** | **none** | **yes (same algorithm)** |

Codegen is the deployment endgame: the solver is baked into the binary, zero heap, zero external dependency — exactly the "comptime-bounded static workspace" issue #12 wanted. The remaining work is wiring it as a `.solve_qp` VM op (the generated `solver` global replaces the cimport workspace).
