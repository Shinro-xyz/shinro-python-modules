# Lab Notes — 2026-09-21

### 2026-09-21 — Issue #19: unified dev CLI over the scenario TOML (Steps 1–4)

**Why.** Issue #19 (2026-09-07) called the trace/compile path a "dirt road":
only two hardcoded generators, no "does my component trace?" gate, MPC needing
two scripts, opt-in verify, and the scenario TOML not actually driving the
build. Most of that had since landed — `gen_scenario` / `build_scenario`, the
strict `[compile]` section, the two-gate oracle, and `run_scenario` moved into
`shinro.simulation.runner` (with a runnable `Scenario` + `SimResult.check()`).
What remained: verify was not wired into `make zig-build`, there was no
`zig-build-mpc`, the CLI was fragmented (`shinro-compile` +
`scripts/trace_component.py` + `verify_deployment`, no `check`/`run`), there
was no explicit compose "recipe" seam, and the deployment record dropped the
build flags that explain why two records differ. Four steps closed those.

---

**Step 1 — `make zig-build-mpc` + verify wired into `make zig-build`** (`a429861`)

- `ZIG_BUILD` / `ZIG_STAMP_VERIFY` shared recipe variables; new `zig-mpc-gen`
  (runs the MPC generator) and `zig-build-mpc`; the `zig-*` targets added to
  `.PHONY` (they were previously unlisted, a latent bug).
- **Design:** `verify_deployment` (producer/verifier separation) now runs in
  the build tail, so a drifted config/graph/binary fails the build instead of
  shipping silently. `zig-build-mpc` uses the shipped default emosqp bake —
  n_vars=30 matches `mpc_lti_base.toml`, so no solver regeneration is needed.
- Docs (`docs/testing.md`) gained a `zig-build-mpc` row.

**Step 2 — build provenance + oracle status in the deployment record** (`8b1d0e4`)

- `stamp(prefix, build_root, name, oracle=None)`; the record gains a `build`
  block (`target`, `optimize`, `stripped`, `zig_version`, `libc`,
  `float_type`, copied verbatim from the build manifest) and an `oracle` block.
- `build_scenario` populates the oracle on every path: `passed` (with
  samples/seed/max_abs_err/tolerance), `not_run` + `reason: cross-compiled`,
  or `not_run` + `reason: unverified build (--scenario omitted)`.
- **Design:** neither block is folded into the master hash. The binary slot
  already distinguishes a Debug from a ReleaseFast build, so these fields
  *explain* a hash change rather than define it — existing record hashes are
  preserved.

**Step 3 — the unified `shinro` CLI** (`3fd3026`)

- Five verbs, each a thin dispatcher over existing APIs: `check` (component →
  factory `create()` + inferred trace contract; scenario →
  `ScenarioFactory.build()`), `run` (`Scenario.run()` + `SimResult.check()`
  against `[scenario.tolerance]`), `trace` (op coverage + interpret-vs-live
  oracle), `build` (gen → zig → oracle → stamp → verify), `verify` (re-hash
  the record).
- The standalone tracer moved from `scripts/trace_component.py` into
  `shinro.codegen.component_cli` — an installed wheel cannot import `scripts/` —
  with the script kept as a shim; `CONFIG_DIR` is now package-relative.
  `compile_scenario()` was extracted from `codegen/cli.py` so the build verb
  shares one implementation. `pyproject` gained `shinro = "shinro.cli:main"`
  (`shinro-compile` stays as the build-only alias).
- **Design:** `build`/`verify` default `--out` to `build/<scenario-stem>`, so
  two scenarios can no longer clobber a shared `build/scenario` dir.

**Step 4 — graph-recipe registry + collapsed generators** (`73deaa4`)

- New `shinro.codegen.recipes`: `@register_graph(name)` / `available_graphs()` /
  `build_recipe(name, spec)`, with `closed_loop_tracking` (estimator +
  controller into the fixed ABC dataflow, plant-derived dims/model) and
  `policy_only` (standalone ONNX policy).
- `gen_scenario` dispatches on `[compile].recipe` (inferred `policy_only` when
  `[estimator]` is absent, else `closed_loop_tracking`); an unknown recipe is
  rejected at load; a non-policy controller with no `[estimator]` is still
  rejected. The ad-hoc `if estimator:` branch, `_policy_graph`, and the
  duplicated provenance-version code are gone.
- The two shipped default graphs (KF+LQR, KF+MPC_LTI) moved into `recipes.py`
  with their config sets declared **once** (`LQR_CONFIGS` /
  `DEFAULT_MPC_CONTROLLER`), so manifest provenance is derived, not hand-listed;
  `scripts/gen_base.py` / `gen_mpc.py` became shims (test imports preserved).
- **Dims are plant-authoritative.** A plant-only `[plant]` (`type` + `config`)
  derives `n_x`/`n_u`; they may be omitted, a declared value that disagrees is
  a **loud error** (mirroring the `[scenario].dt` check), and the derived value
  wins. Docs corrected in `recipes.closed_loop_tracking`, the `scenario_gen`
  module docstring, `_template.toml`, and the derived-model fixture comment —
  the old claim "explicit dims win over derived" was backwards.

**Follow-up — per-mode output dirs + `[compile].out`** (issue #19 items 2 & 3)

- `shinro build`/`verify` now default `--out` to
  `build/<scenario-stem>/<optimize>-<target>`, so a Debug and a ReleaseFast
  build (or a native and a cross build) of the same scenario land in separate
  dirs instead of overwriting each other's graph and record. Precedence is
  `--out` > `[compile].out` > the per-mode default; `verify` gained
  `--optimize`/`--target` to locate the same dir.
- `[compile].out` is a validated schema key (non-empty path) for pinning an
  exact per-target dir; documented in `_template.toml` and `docs/codegen.md`.
- Verified: `make test` 1277 passed / 5 skipped, `make lint` clean.

**Follow-up — MPC bake-on-demand** (issue #19 item 4)

- `[compile].solver = "emosqp"` bakes the static OSQP solver on demand, folding
  the out-of-band `gen_emosqp_test.py` run + hand-pointed `solver_dir` into one
  `shinro build` (gen → bake → zig → oracle B → stamp → verify).
- New `shinro.codegen.bake` (`bake_emosqp` / `bake_is_current` / `SOLVERS`);
  `scripts/gen_emosqp_test.py` wraps it for the Zig oracle vectors. The bake
  lands in the isolated `<out>/emosqp` (per-mode) and is hashed into the
  record's solver slot; it is reused when its `n_vars` + controller-config sha
  still match. `solver` and `solver_dir` are mutually exclusive (the latter
  remains the pre-baked escape hatch); a `solver` on a non-QP graph, an unknown
  name, or a missing `--scenario` are loud errors.
- Key nuance: the **tracer** (not emosqp) produces the `.solve_qp` node; the
  bake is OSQP's C codegen for that problem. The `.so` runs the bake's problem
  while `interpret()` runs the graph's, so **oracle B** — not just the comptime
  `n_vars` check — is what catches a graph↔bake problem mismatch.
- New `tests/integration/scenarios/mpc_compile.toml` proves it e2e (bake →
  oracle B → record `solver.n_vars=30` → second build reuses);
  `tests/test_bake.py` covers bake/reuse.
- Verified: `make test` 1283 passed / 5 skipped, `make test-zig` 83/2,
  `make lint` clean.

**Follow-up — gate A in the build (equivalence, pre-compile)** (issue #19 item 1)

- `shinro build` now runs, pre-compile: **integrity** (the on-disk graph is
  exactly what the scenario produces) then **gate A** — `interpret(composed
  graph)` vs the *live* estimator+controller over 50 ticks. A mismatch fails
  with exit 3 before any compile time or stamping. It closes the one layer
  where a trace/compose bug could yield a self-consistent but wrong graph
  (oracle B and integrity both pass) and still get a "verified" record: the
  stamp now chains `.so == interpret(graph) == live components`.
- New `shinro.codegen.gate_a.run_gate_a` mirrors `compose`'s role mapping, clip
  and `state_*` threading; it runs >1 tick because tick 0 starts both sides
  identical (a frozen recurrence only diverges later). `build.py` split
  `instantiate()` out of `build_composed_graph`, and `recipes` gained
  `closed_loop_configs()` / `live_components()`, so the graph and the live loop
  share one construction. Policy-only graphs skip gate A (no live pair).
- Verified: all shipped scenarios bit-exact (`u_max_err = 0.0` for KF+LQR, MPPI,
  KF+MPC/QP); `tests/test_gate_a.py` also proves a perturbed live gain is caught.
  `make test` 1287 passed / 5 skipped, `make test-zig` 83/2, `make lint` clean.

**Follow-up — cross-compiled `native_ref`** (issue #19 item 5)

- A cross-compiled record now points at the oracle-verified *native* build of
  the same config/graph/solver: `stamp(..., native_record=(path, dict))` adds a
  top-level `native_ref` block (`record`, `master_hash`, `slots_match`). The
  cross build resolves the native record from `--native-record` or the per-mode
  convention `<out>/../<optimize>-native/lib/<name>.deployment.json`.
  `slots_match` compares config/graph/solver (only `binary` legitimately differs
  across targets), so a cross build carries the native verification it cannot
  run itself. Not folded into the master hash — metadata, like `build`/`oracle`.
- Verified: e2e native + cross → `native_ref.master_hash == native master`,
  `slots_match: true`; 3 `_resolve_native_ref` unit tests + 1 zig-gated e2e.
  `make test` 1291 passed / 5 skipped, `make lint` clean.

**Key design decisions.**

- **`[compile]`, not `[deploy]`.** The issue proposed a `[deploy]` section; the
  shipped name is `[compile]`, and renaming would be churn plus a back-compat
  break. Left as-is.
- **Master hash stays a pure function of config/graph/solver/binary.** Build
  flags and oracle status are metadata; folding them in would invalidate every
  existing record for no identity gain.
- **The CLI owns no pipeline logic.** Every verb delegates; the new code is a
  dispatcher plus a per-scenario default output dir.
- **A registry with two real recipes, not a framework.** `policy_only` was
  already a special case; naming both wirings makes selection explicit data
  instead of a section-presence heuristic, and gives the shipped generators a
  shared home.
- **Shipped graph identity is unchanged.** The shipped default graphs are still
  built from declared config sets, so their deployment-record config slot and
  master hash do not change. Using shipped scenario TOMLs would add the
  scenario file to provenance and change that hash — a deliberate deploy-identity
  decision left for later.

## Separate the shipped configs from `src/` → repo-root `samples/`

**What.** Moved the 36 shipped TOMLs from `src/shinro/configs/` to a repo-root
`samples/` directory (subdirs preserved: `controllers/ estimators/ plants/
trajectories/ scenarios/` + `robot_config.toml`) via `git mv`, so history is
preserved. They are now **documentation, not installed data**:

- `pyproject.toml` package-data drops `configs/**/*.toml` (only `runtime/**/*`
  ships now); `MANIFEST.in` drops the recursive-include and gains
  `recursive-exclude samples *`, alongside the existing `tests/`/`demos/`
  exclusions.
- New `samples/README.md` explains the layout, the copy-into-your-project
  workflow, and the resolution contract.

**Why.** Two concrete defects from the previous design, both confirmed by
running it:

1. **Silent basename substitution.** `resolve_config_path` fell back to the
   packaged `shinro/configs` directory by *basename*, so a wrong-CWD relative
   path silently loaded shinro's own config. Verified before the change:
   `resolve_config_path("mysub2/robot_config.toml")` returned
   `src/shinro/configs/robot_config.toml` — the caller's file was ignored with
   no warning.
2. **Shared namespace collision.** Third-party configs referenced as
   `configs/...` collided with shinro's shipped set, and shinro's packaged copy
   won: `configs/controllers/lqr_base.toml` resolved to the packaged file even
   when the user shipped their own under the same name.

**Design decisions.**

- `resolve_config_path` is now **absolute path → CWD-relative → loud
  `FileNotFoundError`**. The packaged fallback, the `configs/`-prefix special
  case, and the basename search are all deleted. The error names the CWD and
  points at `samples/`.
- `get_config_path` removed (0 callers; its only purpose was packaged lookup,
  and `docs/components.md` is updated).
- `component_cli.CONFIG_DIR` now resolves `parents[3]/samples` (repo layout).
  The existing `is_dir()` guard means an installed wheel degrades to a
  registry-only inventory rather than erroring.
- Deduplicated `robot_config.toml`: the repo-root tracked copy (byte-identical
  to the packaged one — verified with `cmp` before deleting) is gone; all refs
  point at `samples/robot_config.toml`. This removes the drift hazard noted on
  2026-09-11.
- The one `chdir` test (`test_cli.py::test_default_out_is_per_mode`) copied the
  samples into `tmp_path`, because CWD-relative resolution is now the only
  contract — a scenario run from another CWD needs its configs there.

**Mechanically.** 46 files / 186 replacements by a byte-level replacer
(`configs/` → `samples/`) that requires the token to be preceded by a quote,
backtick, or the package path, so the separate `tests/fixtures/configs/`
namespace was never touched; a second pass handled bare `configs/<sub>/` forms
in comments/docstrings with a negative lookbehind for `fixtures/`. Then manual
fixes for the segmented path expressions and the doc prose that claimed the
configs were packaged.

**Verification.**

- `make test` — **1298 passed, 5 skipped, 96 deselected**.
- `make lint` — ruff clean; pyrefly 0 errors.
- `make test-zig` — **83 passed, 2 skipped**.
- `src/shinro/runtime/graph_data.zig` is **byte-identical** after `make zig-gen`
  (`sha256 6c11706965d6…`) — the rename changed provenance path strings only,
  never graph content. The manifest gained the `provenance` block that
  `make zig-gen` writes, which resolves the pre-existing drift noted earlier in
  this same note.
- New `tests/test_config_resolver.py` pins the contract: absolute and
  CWD-relative paths resolve; a missing relative path names the CWD; a bare
  filename does not reach the package; the packaged configs dir is gone.

**Pre-existing issues surfaced, deliberately not fixed (out of scope; not in
`make lint`'s pyrefly scope, which covers only `utils/ components.py
controllers/ estimators/ trajectories/ plants/`).** Pyright (via pi-lens)
reports `SimResult` vs `list[StepRecord]` mismatches in
`tests/integration/test_cartpole.py`/`test_pendulum.py`/`test_arm_cartesian.py`
and mujoco-stub errors in `demos/*` + `physics_engine/mujoco.py`. Each of those
files carries only a config-path (or docstring) edit from this change; the
findings reproduce at HEAD and are unrelated to the move.

**Follow-up.** `docs/quickstart.md` now leads with the copy-from-`samples/`
workflow; if an installed-wheel user flow is wanted later, it should ship

## `--import MODULE` — third-party components on the CLI

**What.** Added a repeatable `--import MODULE` flag to the `shinro` CLI (all
five verbs) and to `shinro-compile`. It imports the named module before the verb
runs, so a `@register_*` component defined outside shinro is visible to the
registry.

**Why.** `factories/__init__.py` imports only `shinro.controllers` /
`estimators` / `plants` / `trajectories`, so a third-party `@register_controller`
never ran and `_CONTROLLER_REGISTRY[type]` raised a bare `KeyError`. The only
workaround was a driver script that imported the package first. The flag is that
import, in the CLI.

**Design.**

- New `utils/plugin_loader.py`: `import_modules(names)` +
  `PluginImportError`. Any import-time failure is wrapped with the module name
  and cause, so a typo is a clean CLI error rather than a traceback.
- The flag is accepted **before or after** the verb name
  (`shinro --import p build x.toml` and `shinro build x.toml --import p`). The
  top-level parser owns `default=[]`; the five subparsers re-add the same option
  with `default=argparse.SUPPRESS` so an after-verb flag appends to the same list
  without clobbering a before-verb one.
- `--import` is on `shinro-compile` too, for parity — otherwise a third-party
  component would work on `shinro build` but not on the compile entry point.
- Semantics are dotted module names (`importlib.import_module`), not file paths.

**Also in this change (separate concern, flagged):** a pre-existing annotation
bug in `tests/integration/helpers/assertions.py`. The five helpers annotated
`records: list[StepRecord]` but receive `SimResult`, which is *deliberately*
duck-typed list-like (`simulation/runner.py` implements `__iter__`/`__getitem__`
/`__len__` "so existing test helpers operate on it unchanged"). The helpers only
iterate, so the accurate annotation is `Iterable[StepRecord]` — a strictly weaker
(all-`list`-compatible) type. This was surfaced repeatedly by the Pyright/lens
check on files this branch touched; the underlying mismatch is pre-existing and
does not affect the tests. Can be split out if preferred.

**Verification (observed).**

- End-to-end smoke test with a real out-of-tree `mypkg` registering `SmokeP`:
  - flag after verb → `OK: SmokeP (controller) constructs` (exit 0)
  - flag before verb → same (exit 0)
  - no flag → `ERROR: cfg.toml: type 'SmokeP' is not registered. Registered:
    [...]` (exit 2) — proves the flag is what enables the type
  - `--import nope_xyz` → `ERROR: cannot import 'nope_xyz': ModuleNotFoundError`
    (exit 2)
- New `TestImportFlag` in `tests/test_cli.py` (5 tests) covers the above
  including the inventory path (`trace --import`) and teardown of both
  `sys.modules` and the registry.
- `make test` — **1303 passed, 5 skipped, 96 deselected**.
- `make lint` — ruff clean; pyrefly 0 errors.
- `make test-integration` — **58 passed** (with the `Iterable` annotation).
- Fresh LSP probe on the six integration files: **0 diagnostics**.
- `src/shinro/runtime/graph_data.zig` still `6c11706965d6…` (untouched).

**Docs.** `cli.py` / `codegen/cli.py` docstrings; new quickstart §5 "Third-party
components on the CLI"; `docs/components.md` intro note on what the CLI knows
about depending on what was imported.
