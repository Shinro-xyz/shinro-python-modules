# 2026-09-07

## Graph-conditional OSQP linking for the Zig VM

### What changed

The Zig lowering path now decides whether an OSQP solver belongs in the binary
based on the lowered graph itself, rather than always compiling the generated
static solver into `libbase.so`.

- `lower_zig` now emits `pub const has_solve_qp = true/false` into
  `graph_data.zig` and records the same fact in the graph manifest.
- `build.zig` reads that flag. For QP graphs it wires in the selected
  `-Dsolver_dir`, its headers, C sources, and `solver_meta`. For non-QP graphs
  it omits those entirely and leaves the build manifest's solver provenance as
  `null`.
- `lower.zig` imports `qp.zig` and `solver_meta` only when the graph has a
  `.solve_qp` node, so the OSQP wrapper is not analyzed for LQR/PID builds.
- Updated the Zig lowering tests and docs to describe the solver-free path and
  the conditional manifest fields.
- Excluded the generated `runtime/codegen/emosqp/setup.py` from Ruff because it
  is generated OSQP output, not source we format.

### Why

The default graph is KF + LQR and has no `.solve_qp` node, yet the build was
still linking the whole OSQP codegen bake. This made non-MPC binaries carry
solver code they can never call. The graph is the authoritative source of truth
for whether the deployed step performs QP, so making the graph carry that
decision lets Zig build one self-consistent binary per controller scenario.

### Key design decision

Keep the decision in generated graph data, not a separate build flag. This
preserves the existing contract that one graph is one deployment artifact and
avoids asking the caller to remember whether the graph contains a QP. The
`has_solve_qp` flag is cheap and deterministic, and the existing comptime
graph↔bake `n_vars` check still applies when QP is present.

### Test results

- `ZIG_GLOBAL_CACHE_DIR=/tmp/shinro-zig-cache make test-zig` — 15 passed.
- `make zig-build` — passed with the shipped KF + LQR graph.
- `ruff check .` — passed after excluding the generated OSQP setup file.
- Local ReleaseFast size check: KF + LQR `libbase.so` was about 201 KB versus
  267 KB for KF + MPC_LTI (about 66 KB smaller with OSQP omitted). The LQR
  manifest reported `solver: null` and `nm -D` showed no OSQP/QDLDL symbols.

### Deployment master hash — config/graph/binary tracking

### What changed

Added a post-compile **deployment record** that gives every build a single
master hash committing to the whole config → graph → solver → binary chain,
so teams can answer "which estimator/controller pair is deployed, and has
anything drifted?" without rebuilding.

- `scripts/gen_emosqp_test.py` — `solver_meta.zig` now records
  `config_sha256` (sha256 of the resolved config's raw bytes) plus the
  python/numpy/scipy/osqp versions. The generic `solverMetaJson()` parser in
  `build.zig` surfaces them in the build manifest with zero build changes.
- `src/shinro/codegen/lower_zig.py` — `lower_zig()` gained an optional
  `provenance` dict, merged into the graph manifest. Stays generic/opaque.
- `scripts/gen_base.py` / `scripts/gen_mpc.py` — pass provenance: the config
  paths + sha256 they consumed, plus python/numpy versions. `gen_mpc.main()`
  derives the controller config from its actual argument.
- `scripts/stamp_deployment.py` (new) — post-compile step wired into
  `make zig-build`. Reads the build manifest, hashes `libbase.so` and the
  baked solver tree, writes `libbase.deployment.json` (master hash + per-slot
  drill-down) and a timestamped archive copy under `deployments/`.
- `scripts/verify_deployment.py` (new) — independent re-hash of the artifacts
  against the record (producer/verifier separation); exit 0 on match, 1 on
  drift. Catches a config edited after the bake with no rebuild.
- `.gitattributes` — `*.toml text eol=lf` pins TOML checkouts to LF so the
  byte-level config hashes are reproducible across platforms (Windows
  `core.autocrlf` would otherwise flip them).
- `tests/test_zig_lowering.py` — new `TestDeploymentRecord` class (5 tests):
  master-hash/slot shape, determinism, archive copy, verify pass + drift
  detection, and graph-provenance plumbing. `_build_so` gained a
  `provenance` param.

### Why

The build manifest tracked the *build* (graph sha, solver facts) but never
hashed the `.so` itself, and configs were recorded only as path strings — so
config drift was invisible and a deployed binary couldn't be verified without
rebuilding. The master hash closes both: `binary_sha256` is the ground truth
of what's deployed, `config_sha256` makes drift detectable read-only.

### Key design decisions

- **Master hash computed in Python post-compile, not `build.zig`** — the
  manifest is written at configure time, before the `.so` exists, so the
  binary slot can't be computed there. A separate record file
  (`libbase.deployment.json`) keeps `build.zig`'s manifest a pure
  configure-time artifact.
- **Fixed 4-slot structure with a sentinel** (`sha256(b"")`) for the solver
  slot — LQR/PID and MPC deployments stay structurally comparable; switching
  controllers changes slot *values*, never the shape.
- **Flat hash for the solver slot** (not a Merkle tree) — 40 files, flat is
  90% of the value; the tree only earns its keep for membership proofs.
- **Config hash is hermetic** — hashes the resolved file's raw bytes;
  `config_resolver.py` is path-only (no preprocessing), so the hash covers
  exactly what the factories consumed.
- **Source code deliberately excluded** — the master hash means "configs +
  generated + binary", not "the whole software". Editing a controller `.py`
  without regenerating is invisible (documented residual risk; process
  discipline mandates regeneration).

### Test results

- `make test-zig` — 20 passed (15 existing + 5 new deployment-record tests).
- `make lint` — ruff + pyright clean.
- Manual cross-check: `stamp_deployment.py` binary slot == `sha256(libbase.so)`;
  `verify_deployment.py` returns 0 on match, 1 after tampering a config byte.
- Determinism: re-stamping the same build produces a byte-identical record
  (archive filename differs by timestamp only).

### 2026-09-07 18:30 UTC — standalone component tracer (`scripts/trace_component.py`)

Phase 2 of the unified-CLI issue (#19): a standalone "does my component
trace?" gate, no build machinery. Three modes in one script:

- **Inventory** (no args) — every registered controller/estimator/trajectory/
  plant, cross-referenced with the config TOMLs that exist for them (matched
  on each file's `type` field).
- **Contract** (`--list <config>`) — the inferred trace contract
  (`Type.method(input_names)`), so users discover what shapes to pass.
- **Trace + oracle** (`<config> --shape ... [--state ...]`) — `trace_node`,
  node count + op histogram + `has_op` coverage, then the oracle check:
  re-execute the captured graph with `interpret()` on the same random inputs
  as a live component call, asserting **bit-exact** agreement per output and
  `state_*` port. Exit codes: 0 green · 1 untraceable · 2 usage/config · 3
  oracle mismatch.

Design decisions:

- **Shapes are explicit flags, not guessed.** Configs don't declare dims
  (`lqr_base.toml` is just costs), so `--shape name=SPEC` / `--state name=SPEC`
  (SPEC = `3`, `3x1`, `3x3`, `scalar`). `--list` makes discovery cheap.
- **Square 2-D state inputs are SPD-ified** (`A@A.T + 0.1·I`) so covariance
  states (KF's `P`) stay invertible for the oracle — mirrors the test-suite
  convention.
- **Any trace failure is a clean "not traceable" report** (exit 1), not a
  traceback — the script's contract is to answer the question, including
  "no".

Findings (the script earning its keep):

- **Fixed a real bug in `PID.from_config`**: gains were passed through
  `bk.from_numpy(...)`, which is a no-op for `NumpyBackend`, leaving `self.ki`
  etc. as Python lists. Works under numpy (list·array broadcasting) but
  crashes the `TraceBackend` (`zeros_like(list)` → AttributeError), so PID
  was untraceable via config. Switched to `bk.array(...)` (matching LQR).
  No test depended on list gains; full suite green.
- **SMC is not traceable as-is** — `self.bk.array(x).flatten()` calls
  `.flatten()` on a `Tracer` (no such method). Would need a `flatten` op.
- **Plants with state indexing are not traceable as-is** —
  `self.state[2]` on a pre-injected state `Tracer` (no `__getitem__`).
- **Trajectory `from_config` returns schedule data, not a component** — the
  script detects this and reports "not standalone-traceable" (exit 2).

Test results: `tests/test_trace_component.py` — 13 passed (LQR, KF w/ SPD
state, PID w/ 3 state ports, SMC untraceable, trajectory non-component,
exit codes, CLI subprocess modes). `make lint` clean; `make test` 968 passed,
5 skipped, 73 deselected.

### E2E scenario compilation pipeline (gen_scenario → build_scenario)

### What changed

Closed the gap between "trace a component" and "deploy a `.so`": an external
user with a different robot can now compile their estimator + controller into
a verified, stamped `libbase.so` from a single scenario TOML — no bespoke
generator scripts.

- `src/shinro/codegen/build.py` (new) — generic `build_composed_graph(
  estimator_config, controller_config, n_x, n_u, input_limits)` with a
  **two-pass trace** (`_trace_with_state`): pass 1 attr-diffs to discover
  recurrent state, pass 2 re-traces with those attrs pre-injected as `state_*`
  ports. This is what makes component swaps (KF→Luenberger, LQR→PID) compose
  with zero per-component declaration. Controller inputs map to shapes by role
  (`u_prev` → `(n_u,)`, else `(n_x,)`); estimator inputs follow the repo's
  `(n,1)` column convention.
- `scripts/gen_base.py` / `scripts/gen_mpc.py` — refactored onto
  `build_composed_graph` (thin wrappers now; provenance preserved).
- `scripts/gen_scenario.py` (new) — zig-free stage: reads a scenario TOML's
  `[controller]`/`[estimator]` configs, `[scenario].input_limits`, and the new
  `[compile]` section (`n_x`, `n_u`), traces + composes + lowers to an
  **isolated** path (never clobbers `runtime/graph_data.zig`). Records the
  scenario TOML's own sha256 in provenance, so the deployment record commits
  to the whole build spec.
- `scripts/build_scenario.py` (new) — zig stage: pre-flight zig check (exit
  5), build flags from `[compile]` (CLI > TOML > default), `zig build
  -Dgraph=<abs>`, **integrity check** (re-gen + byte-compare manifests —
  deterministic lowering proves the `.so` was built from exactly this
  scenario's graph), **oracle B** (ctypes `shinro_step` vs `interpret()` on N
  random inputs, tol 1e-12 / 1e-3 for QP), then `stamp_deployment` +
  `verify_deployment`.
- `Makefile` — `make compile SCENARIO=...` chains the two scripts.
- `tests/test_compile_scenario.py` (new) — 8 tests: `[compile]` validation,
  gen-vs-shipped graph equivalence, e2e verified build, stale-graph rejection,
  shared-path-untouched.
- `tests/integration/scenarios/base_tracking.toml` — added `[compile]`
  (`n_x = 3`, `n_u = 3`).

### Why

The compile-to-`.so` path was "folklore": `make zig-build` only built the
shipped KF+LQR graph, and a different robot meant hand-copying `gen_base.py`
and editing it. The framework pieces (`trace_node`, `compose`, `lower_zig`,
the Zig VM) were already generic — only the generator scripts hardcoded
LeKiwi. This makes the scenario TOML the single reproducible build spec: one
config drives both simulation (`ScenarioFactory`) and compilation.

### Key design decisions

- **`[compile]` section is the build spec** — `n_x`/`n_u` (baked at trace
  time), `optimize` (`debug`/`release` → ReleaseFast only; ReleaseSafe hangs
  in `osqp_solve`, ReleaseSmall unvalidated), `target` (cross-compile),
  `solver_dir` (required for QP graphs). Unknown keys and invalid `optimize`
  are loud errors (exit 2) — a typo must not silently change the build.
- **Two scripts, unified by make** — `gen_scenario.py` (zig-free, testable in
  CI without zig) and `build_scenario.py` (zig + oracle + stamp + verify).
  The handoff contract is `graph_data.zig` + its manifest; provenance flows
  through the existing chain (graph manifest → build manifest → deployment
  record) with zero new coupling.
- **`--scenario` makes "verified" possible** — the oracle needs the Python
  `ComposedGraph` (not the Zig table), so `build_scenario.py` re-runs the gen
  stage in-process and byte-compares manifests (integrity) before trusting the
  oracle. Omitting `--scenario` is allowed-with-warning (build-only,
  unverified).
- **Exit codes** — 0 ok · 1 untraceable · 2 usage/config · 3 oracle mismatch
  · 4 build/verify failure · 5 zig missing (pre-flight, before any work).

### Test results

- `make test` — 978 passed, 5 skipped (8 new e2e tests).
- `make test-zig` — 20 passed (refactor fidelity: all KF+LQR/PID/MPC oracles
  green against the refactored `build_base_graph`).
- `make compile` — end-to-end green on `base_tracking.toml`; oracle max abs
  err 4.996e-16; `--optimize release` → ReleaseFast + stripped, ~200 KB.
- `make lint` — ruff clean.
- Failure paths verified: zig missing → 5, corrupt manifest → 2, stale graph
  → 2, QP graph without solver → 2.
- `runtime/graph_data.zig` untouched after custom compiles (isolated
  `-Dgraph`).

### Generic scenario config template

### What changed

Added `src/shinro/configs/scenarios/_template.toml` — a commented scenario
skeleton for external users with a different robot. Copy it, fill in the
placeholders (controller config, estimator config, `[compile]` `n_x`/`n_u`),
and run `make compile`. The template documents every field the schema
supports: required vs optional sections, valid `optimize` values, the
`target`/`solver_dir` options, and which sections the simulation path needs
vs. the compile path (the sim block is commented out with a "delete for
compile-only robots" note).

Also added a drift-guard test (`test_scenario_template_stays_in_sync_with_compile_schema`):
the template must parse as TOML, use only known `[compile]` keys, and mention
every schema key (active or commented) — so a future `[compile]` schema
addition forces the template to document it.

### Why

The e2e pipeline works, but a new user had no starting point: the only
scenario TOMLs were LeKiwi simulation scenarios in `tests/integration/`
(carrying `[sim]`/`[physics]`/`[plant]` sections that don't resolve from an
installed wheel). The template makes the minimal compile-only scenario shape
explicit and copy-pasteable.

### Key design decisions

- **Config-as-documentation** — the template is the schema documentation, in
  the same format the pipeline consumes. No script changes; `load_scenario`
  already accepts the minimal form.
- **`_` prefix** signals "not runnable"; the `trace_component.py` inventory
  ignores it (scenario files have no top-level `type`).
- **Placeholders are valid TOML** — `n_x = 2  # <fill in>` rather than
  `n_x = <2>`, so the file parses and the drift-guard test can read it.

### Test results

- `tests/test_compile_scenario.py` — 9 passed (8 existing + 1 drift guard).
- Manual: filled the template with the shipped LQR/KF configs and `n_x=n_u=3`
  → `gen_scenario.py` produces the same 50-node graph as `base_tracking.toml`;
  wrong dims (2 vs 3-DOF configs) → clean exit 2 (ShapeMismatchError is a
  ValueError, caught as usage error).
- `make lint` — ruff clean.
