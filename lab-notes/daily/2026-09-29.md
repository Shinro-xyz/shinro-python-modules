# 2026-09-29 — B-spline trajectory generator: Cox–de Boor derivatives

Branch: `main`

## Why

The user's `src/shinro/trajectories/b_spline.py` draft had a working Cox–de
Boor basis recursion but no working component: `_bspline_derv` handled only the
`k == 0` and `k > p` cases (falling off the end of the function for
`0 < k <= p`), `position_at` computed `pos` and returned nothing, `generate`
only set `self.T`, and the class was decorated `@register_trajectory("bspline")`
while `register_trajectory` is `strict=True` about a frozen `Config` — so the
first import of the module (via `trajectories/__init__.py`) would have raised.
The task: complete `_bspline_derv` so derivatives reuse the same Cox–de Boor
recursion, and wire the class into the framework.

## Math decision — derivatives by degree reduction

Rather than differentiate the basis functions term-by-term, the k-th derivative
curve is represented as **another B-spline**: one differentiation step maps a
degree-`p` curve to a degree-`p-1` curve over the scaled control-polygon
differences

```text
Q_i = p (P_{i+1} − P_i) / (u_{i+p+1} − u_{i+1})
```

with one knot chopped from each end of the vector. Applied `k` times it gives
the k-th derivative curve as a B-spline of degree `p − k`, which is then
evaluated with the *same* `_bspline_basis` / `_all_basis` recursion — no second
derivative formula to maintain. `_bspline_derv` returns
`(points, degree, knots)` for that reduced curve:

- `k == 0` → the input curve unchanged;
- `k > p` → the derivative is identically zero, represented as a degree-0 curve
  on a zero control polygon (`zeros_like(P)`), with knot vector of length
  `len(P) + 1` so the basis count matches the control count;
- otherwise → one degree-reduction step and recurse on `(k−1, p−1)`.

This mirrors `BezierCurve`, whose derivatives are themselves lower-degree
Bézier curves.

## What changed

- `src/shinro/trajectories/b_spline.py`:
  - `_bspline_derv` completed (degree-reduction recursion above).
  - `_bspline_basis` / `_all_basis` take an optional `knots` argument
    (defaulted to `self.knots`) so derivative curves can be evaluated on their
    **reduced** knot vectors; the recursive Cox–de Boor calls now thread
    `knots` through (pi-lens had added the parameter but not passed it down, so
    a reduced-vector eval would have silently recursed onto `self.knots`).
  - `_eval_curve(points, p, knots, t)` helper (clip + basis row + matmul).
  - `generate(duration, start_position=None, end_position=None)` validates

    `len(knots) == len(P) + p + 1`, nondecreasing knots) and precomputes the
    velocity/acceleration derivative curves (`k = 1, 2`). Start/end are
    informational only — a *general* B-spline does not interpolate its ends
    (only a clamped vector does), so no agreement check is implied.
  - `position_at(t)` returns `(pos, vel, acc)` like `BezierCurve`.
  - `BSplineConfig` (`dt`, `duration`, `degree`, `control_points`, `knots`,
    `name="bspline"`) + `from_config` — required by the strict registry, and the
    same waypoint-schedule contract as the other generators.
  - Corrected the control-point annotation (`list[float]` → `list[list[float]]`;
    each control point is a vector, as `len(p)` in validation assumes).
- `src/shinro/trajectories/__init__.py` — export `BSpline` (+ `__all__` and the
  module docstring) so registration actually runs and the API docs pick it up.

## Design decisions / notes

- Derivative order is baked at `generate` time (`_vel_curve`, `_acc_curve`);
  `position_at` is then three identical `_eval_curve` calls. A degree-0 curve's
  velocity and a degree-<2 curve's acceleration are exact zeros via the `k > p`
  branch, matching `BezierCurve`'s degree-1 zero acceleration.
- Zero-denominator knot spans in the differentiation map to a zero control
  point (the corresponding basis is identically zero), mirroring the `denom > 0`
  guard in `_bspline_basis`.
- Non-clamped knot vectors are accepted; for uniform interior knots the curve
  domain is `[u_p, u_{m+1}]`, not `[0, T]` — `position_at` clips `t` to `[0, T]`
  and evaluates the Cox–de Boor partial sums outside the domain rather than
  erroring (documented behaviour, same as the draft).
- `k > p` zero curve: the draft returned `zeros((len(P), 1))` with a 2-knot
  vector, whose basis count is 1 — a shape error for `len(P) > 1`. Replaced by a
  zero polygon of the right shape with a padded knot vector.

## Verification

- Clamped cubic B-spline (`knots = [0,0,0,0,1,1,1,1]`, 4 control points) is by
  construction a cubic Bézier: `position_at` matches `BezierCurve` on
  pos/vel/acc to **4.4e-16**; `C(0) = P[0]`, `C(T) = P[3]`, boundary velocities
  `3·(P₁−P₀)` / `3·(P₃−P₂)`.
- Cross-checked against `scipy.interpolate.BSpline` (sampling inside the valid
  knot domain): uniform cubic 7-point curve matches at **8.9e-16**; a randomized
  sweep of 300 curves (degree 0–4, random interior knots, numpy dim 3) matches
  position **and** `derivative(1)/derivative(2)` to **3.6e-12**.
- Sanity: partition of unity `Σ N_i = 1`; finite-difference velocity == analytic
  velocity; degree-0 vel/acc and degree-1 acc exact zeros; validation branches
  (knot count, non-monotone knots, non-positive duration) raise `ValueError`.
- `ruff check .` + `pyrefly check ... trajectories/` (`make lint`) — clean,
  0 errors.

## Catmull-Rom trajectory (C¹ waypoint pass-through)

### Why

Design discussion following the B-spline work: the framework had no way to
"pass through" an ordered list of waypoints smoothly.
- `waypoints` is a **piecewise-constant hold** (jump between positions).
- `cubic_segments` / `quintic_segments` generate each `[[segments]]` entry
  **independently and default the boundary velocity/acceleration to zero**, so
the registered behaviour is **stop-and-go** — the curve comes to rest at every
waypoint. Continuity is possible only if the author hand-writes matching
`start_vel`/`end_vel` (and accels) across adjacent segments, which nothing
derives or checks.
- `bezier` / `bspline` take raw control points (the curve does not pass through
  interior control points).

So the missing primitive is a **C¹ interpolating** generator. The key insight
(and the reason this is small): the polynomial **primitives already accept
arbitrary boundary velocities**, so no new math is needed — derive a velocity at
each waypoint and call `CubicPolynomial.generate` per hop.

### Design decisions

- **Catmull-Rom tangents, reused cubic.** Interior velocity
  `v_i = (P_{i+1} − P_{i−1}) / (d_{i−1} + d_i)`; each tangent is the `end_vel` of
  one segment and the `start_vel` of the next, so the concatenation is C¹ by
  construction. Each hop is one `CubicPolynomial` (closed form, **no linear
  solve**) — direct reuse of the existing primitive.
- **Endpoints.** Default `endpoint_tangent = "zero"` (rest-to-rest start/stop,
  the useful robot convention). `"one_sided"` uses `(P₁−P₀)/d₀` /
  `(Pₙ−Pₙ₋₁)/dₙ₋₁` — the classic Catmull-Rom ends — and is what makes a
  collinear/equal-spacing list integrate to a constant-velocity line.
- **Config shape.** `start` (waypoint 0) + `[[waypoints]]` entries
  `{duration, position}`, where `duration` is the travel time *from the previous
  waypoint*. Chosen over a `[[segments]]` list to avoid duplicating shared
  endpoints, and over per-entry hold times to make the pass-through semantics
  explicit. Registered as `catmull_rom` (a **fresh** name — `cubic_segments`
  etc. are taken and carry the registration-overwrite quirk).
- **C² variant.** Not shipped; it would derive second derivatives via a
  tridiagonal solve and still reuse `CubicPolynomial` (converting to Hermite
  velocities), or use `QuinticPolynomial`. Only worth it if acceleration
  continuity is actually required.

### What changed

- `src/shinro/trajectories/catmull_rom.py` (new) — `CatmullRom(TrajectoryGenerator)`
  with `generate(waypoints, durations, endpoint_tangent=...)`, `_tangents`,
  `position_at`, `from_config`; frozen `CatmullRomWaypointConfig` /
  `CatmullRomConfig`; `@register_trajectory("catmull_rom")`. Backend-agnostic
  (`self.bk`), N-dimensional for free.
- `src/shinro/trajectories/__init__.py` — export `CatmullRom`.
- `samples/trajectories/catmull_rom.toml` — 4-waypoint sample.
- `docs/components.md` — `catmull_rom` row.
- `tests/test_trajectories.py` — `TestCatmullRom` (14 cases × numpy/torch):

  equality at joints (C¹), central-difference velocity across a joint, zero vs

  N-dim shapes, validation (fewer than 2 waypoints, duration-count mismatch,

## C — feedforward derivative schedules (`derivatives` opt-in + sampler)

### Why

Every `from_config` did `pos, _, _ = traj.position_at(...)`: the velocity and
acceleration the generators already compute were **thrown away**, so a
tracking controller had only a position reference. Investigation also showed
**no controller consumes a reference derivative today** (`runner._compute_control`
passes a single `reference` vector; `lqr`/`pid`/`mpc_lti`/`mppi` are
position-only) and the closed-loop runner indexes `traj[step]` as a flat
position — so this is a **trajectory-side** capability, non-breaking by design
(a velocity-tracking controller is a separate controller change).

### Design

- **Shared sampler** `src/shinro/trajectories/sampling.py`:
  `sample_schedule(traj, dt, duration=None, order=2)` and
  `sample_segments(segments, dt, order=2)` return a dict of stacked
  `(steps, N)` arrays (`position`, +`velocity` for `order >= 1`, +`acceleration`
  for `order >= 2`). `total_duration` tolerates the `self.T` / `self.duration`
  attribute split. This also **deletes the duplicated sampling loop** from
  every `from_config`.
- **Opt-in** `derivatives: bool = False` on the six curve/segment Configs
  (`bezier`, `bspline`, `catmull_rom`, `lissajous`, `cubic_segments`,
  `quintic_segments`). When true, `from_config` returns the dict; otherwise the
  position schedule exactly as before. `waypoints` (piecewise-constant) and
  `phase_list` (multi-signal) are deliberately excluded.
- Their `from_config` return annotations became `-> Any` — the return is
  genuinely `array | dict`, and without the annotation pyrefly inferred
  `dict | array` and broke existing `.shape`/`[0]` accesses in the tests.

### What changed

- `src/shinro/trajectories/sampling.py` (new) — `sample_schedule`,
  `sample_segments`, `total_duration`.
- `bezier_curve.py`, `b_spline.py`, `catmull_rom.py`, `lissajous.py`,
  `cubic_polynomial.py`, `quintic_polynomial.py` — `derivatives` config field +
  `from_config` via the shared sampler + `-> Any` return annotation.
- `quintic_polynomial.py` — the two `int(np.round(x))` in
  `WaypointSchedule`/`PhaseSchedule` became `round(x)` (removing the last `np.`
  use, so the numpy import went too).
- `src/shinro/trajectories/__init__.py` — export `sample_schedule`,
  `sample_segments`.
- `docs/components.md` — "Reference derivatives" subsection.
- `tests/test_trajectories.py` — `TestDerivativeSchedules` (default unchanged;
  opt-in dict keys/shapes/position equality; finite-difference velocity) over
  all six generators × numpy/torch, and `TestSamplingHelpers` (order
  0/1/2 keys, `duration` defaulting to the generator, segment concatenation).

### Verification

- Smoke over all six: default shape `(steps, N)`, opt-in dict with matching
  positions and non-zero velocity.
- `python3 -m pytest tests/test_trajectories.py tests/test_factories.py` —
  **246 passed** (was 204; +42).
- `make test` — **1669 passed, 5 skipped, 96 deselected** (+42).

## D — Akima + natural cubic-spline waypoint trajectories

### Why

The waypoint surface had only `catmull_rom` (C1, and it can overshoot a steep
change) plus the stop-and-go segment generators. Two common interpolation
behaviours were missing: **overshoot-resistant** (Akima) and **C2 / minimum
curvature** (natural cubic spline).

### Design

- A shared base `_WaypointSpline(TrajectoryGenerator)` holds the plumbing:
  validation, building one :class:`CubicPolynomial` per hop, `position_at`, and
  `from_config` — subclasses implement only `_tangents(points, durations)`.
  Both splines are therefore **cubic Hermite** curves over the same primitive
  (matching the Catmull-Rom design), differing only in the waypoint tangents.
- **`akima`** — local four-interval-slope estimate
  `t_i = (|s_{i+1}-s_i| s_{i-1} + |s_{i-1}-s_{i-2}| s_i) / (|s_{i+1}-s_i| +
  |s_{i-1}-s_{i-2}|)`, applied elementwise (falls back to the slope average
  where the denominator vanishes), with linearly extrapolated end slopes. No
  solve; C1; designed not to overshoot.
- **`cubic_spline`** — natural cubic spline: interior second derivatives solve
  a tridiagonal system (`bk.solve`), `M_0 = M_n = 0`; the Hermite velocities are
  `v_i = (P_{i+1}-P_i)/h_i - h_i(2M_i+M_{i+1})/6`, which reproduces the spline
  segment exactly, so the curve is C2. Global; can overshoot.
- Config shape mirrors `catmull_rom` (`start` + `[[waypoints]]{duration,
  position}`), plus the `derivatives` opt-in from C. Registered `akima` and
  `cubic_spline`; `CatmullRom` was deliberately **not** refactored onto the
  shared base (keeps the diff additive).

### What changed

- `src/shinro/trajectories/waypoint_splines.py` (new) — `_WaypointSpline`,
  `Akima`, `CubicSpline`, `WaypointEntry`, `AkimaConfig`, `CubicSplineConfig`.
- `src/shinro/trajectories/__init__.py` — export `Akima`, `CubicSpline`.
- `samples/trajectories/akima.toml`, `samples/trajectories/cubic_spline.toml`.
- `docs/components.md` — two rows.
- `tests/test_trajectories.py` — `TestAkima` / `TestCubicSpline` (7 cases each ×
  numpy/torch): pass-through, C1 at joints, C2 + natural end acceleration
  (cubic spline), no-overshoot on a flat-then-step dataset (Akima) and the
  contrast overshoot (cubic spline), single-hop linear fallback (Akima),

- `tests/test_factories.py` — `test_create_akima`, `test_create_cubic_spline`.

### Verification

## E — min-snap + circular arc trajectories

### Why

Two motion primitives with no equivalent in the package: a 7th-order
point-to-point for quadrotor-style moves (minimise snap), and an analytic
circular/helical arc for drawing/welding-style paths.

### Design

- **`min_snap`** — `MinSnapPolynomial`, 7th order (8 coefficients) with
  position/velocity/acceleration/**jerk** pinned at both ends, fixed by one
  8x8 `bk.solve`. Zero boundaries give the rest-to-rest minimum snap
  `p0 + Δp(35s⁴ − 84s⁵ + 70s⁶ − 20s⁷)` — the 7th-order sibling of the
  min-jerk quintic. Exposed as a **single** config (`start`, `end`, `duration`,
  optional boundary `v/a/j`), not a `[[segments]]` list: it is one polynomial,
  and `min_snap_segments` would be a clunky name. Jerk is **input-only** — the
  framework's `position_at`/`sample_schedule` carry a 3-tuple (pos, vel, acc),
  so the jerk/snap *profiles* are not emitted.
- **`circular_arc`** — `CircularArc`, analytic (no solve):
  `p(t) = c + r cosθ + (n̂×r) sinθ + n̂ (pitch/2π) θ`, `θ = ωt`,
  `ω = sweep_angle/T`. Constant speed `ωr`, centripetal acceleration
  `−ω²·(in-plane radius)`. Config `center`/`start`/`sweep_angle`/`duration`
  plus optional `normal` (default `+z`) and `pitch` (axial advance per full
  turn → helix). The `start`-point form (rather than `radius` + angles) avoids
  any convention for which in-plane axis is angle 0; `start − center` must be
  ⟂ to `normal` (loud error otherwise).
- Both inherit the `derivatives` opt-in from C via `sample_schedule`.

### What changed

- `src/shinro/trajectories/min_snap.py`, `src/shinro/trajectories/circular_arc.py`
  (new) + exports in `__init__.py`.
- `samples/trajectories/min_snap.toml`, `samples/trajectories/circular_arc.toml`.
- `docs/components.md` — two rows.
- `tests/test_trajectories.py` — `TestMinSnap` (7 × numpy/torch: closed form,
  endpoints, zero/non-zero boundary derivatives, finite-difference velocity,
  bad duration, `from_config`+derivatives) and `TestCircularArc` (8 × numpy/
  torch: constant radius, quarter-turn endpoints, full-turn closure, speed +
  centripetal acceleration, tilted plane, helix pitch, validation,
  `from_config`+derivatives).
- `tests/test_factories.py` — `test_create_min_snap`, `test_create_circular_arc`.

### Verification

- Smoke: min-snap matches the closed form to **3.9e-14**, endpoints exact,

## Time scaling (`time_scaling.py`) — uniform dilation + S-curve

### Why

No generator respects velocity, acceleration, or jerk limits — durations are
hand-picked, so a reference can demand more than the plant can produce. This
closes the functional gap flagged in the trajectory-library review with two
time-scaling strategies (same geometry, different clock).

### Design

`src/shinro/trajectories/time_scaling.py` (renamed from `limits.py` — "time
scaling" is the standard term; "dilation" is a metaphor):

- **Uniform (constant) time scaling** — `time_scale_factor(traj, max_velocity=,
  max_acceleration=, samples=1000)` samples `position_at`, takes the peak
  component speed/acceleration, and returns `k = max(1, peak_v/v_max,
  sqrt(peak_a/a_max))`. `TimeScaled(inner, k)` evaluates
  `inner.position_at(t/k)` and rescales the derivatives (÷`k`, ÷`k²`); `T` grows
  to `k·inner_T`. `limit_trajectory` = `TimeScaled(traj, time_scale_factor(...))`.
- **Min-jerk (S-curve) time scaling** — `s_curve_horizon(...)` re-times the path
  parameter with the min-jerk profile `σ(s) = 10s³ - 15s⁴ + 6s⁵`:
  `p_out(t) = p(T·σ(t/T'))` with chain-rule derivatives. Each output derivative's
  peak is a fixed function of the horizon — `max|v| = T·V/T'`,
  `max|a| = A/T'²`, `max|j| = J/T'³` (with `V, A, J` sampled from the path) — so
  `T'` is the largest of the three solved bounds, floored at `T` (never speeds
  up). `SCurveScaled` applies the time law; `s_curve_limit` combines the two.
  Jerk is finite-differenced (generators expose no `p'''`). Rest-to-rest: the
  ends come to rest (`σ'(0) = σ'(1) = 0`).

Design notes:
- **Programmatic, not TOML-wired**: the registry's `from_config` returns sampled
  arrays, not generator objects, so there is no generator to wrap at the config
  layer. TOML wiring would need a generator-building path.
- `ArrayBackend` has no `max`, so max-abs is `-bk.min(-bk.abs(x))`.
- `.item()` (not `float()`) for the scalar extraction — the static-analyser's
  unchecked-throwing-call rule flags `float()`/`int()`.
