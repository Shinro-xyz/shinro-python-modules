Added a comment in `runtime/build.zig` documenting how to build a production
binary (`-Doptimize=ReleaseSafe` / `-Doptimize=ReleaseFast`). The user then
asked to measure release sizes and keep an eye on component-switch compile
times, which turned into a debugging session.

**Measurements (8-core, warm cache, default graph):**

| Mode | Cold build | libbase.so | `.text` | `.debug_*` | data/tls |
|---|---|---|---|---|---|
| Debug | ~16 s | 12.2 MB | 2.17 MB | 3.17 MB | 509 KB |
| ReleaseSafe | ~41 s | 3.5 MB | 429 KB | **2.85 MB** | 370 KB |
| ReleaseFast | ~31 s | 3.8 MB | 418 KB | **3.20 MB** | 345 KB |

Release binaries are ~80 % DWARF debug info. Stripping drops them to roughly
350–360 KB.

**Component-switch incremental build times:**

| Switch | Python gen | `zig build` | total |
|---|---|---|---|
| KF+LQR → KF+MPC_LTI | 1.5 s | 1.1 s | ~2.6 s |
| KF+MPC_LTI → KF+LQR | 1.3 s | 1.0 s | ~2.3 s |
| KF+MPC_LTI → KF+MPC_DeltaU (new bake) | 2.1 s | 1.3 s | ~3.5 s |

Swapping controllers/estimators is cheap because only `graph_data.zig` changes;
the VM, linalg, and OSQP C are cached by content hash.

**Blocker discovered:** `zig build -Doptimize=ReleaseSafe` and `-Doptimize=ReleaseFast`
hang in `osqp_solve`. The same OSQP C sources compiled with `zig cc -shared -O2`
into a C-only `.so` solve correctly, so the bug is in how `zig build-lib` links
the static OSQP solver into a release shared library (not C flags, UBSan,
`-fstrip`, CPU target, or solver data being lost). I tried:

- `.strip = true/false` — no effect on the hang.
- `-fno-sanitize=undefined -fno-strict-aliasing` and `-O0` for the C sources.
- `-Dcpu=baseline`.
- Prebuilt object files compiled with `zig cc -c`.

All still hang inside `zig build-lib` release builds.

**State left behind:** `runtime/build.zig` is back to the clean comment-only
change; Debug builds and `make test-zig` still pass (15/15). No production-ready
release path until the `build-lib` hang is resolved.

**Next options:**

### 2026-09-04 15:00 UTC — resolved: ReleaseFast is the production mode

The user asked why `-Doptimize` alone doesn't work. Re-testing the modes one at
a time showed the hang is **ReleaseSafe-only**: `zig build
-Doptimize=ReleaseFast` runs correctly. Resolution:

- **`-Doptimize=ReleaseFast` + strip = 269 KB, verified correct.** One-tick
  smoke test matches Debug exactly; the 100-tick KF+MPC live oracle passes with
  max abs err 2.409e-4 (identical for unstripped and stripped binaries — strip
  is numerics-neutral, it only drops DWARF).
- **ReleaseSafe hangs in `osqp_solve`** regardless of strip / UBSan flags /
  C `-O0` / `cpu=baseline` / prebuilt objects. Same C sources via `zig cc
  -shared -O2` solve fine. A Zig `build-lib` release-safe integration bug —
  worth reporting upstream, but it does not block shipping.
- **ReleaseFast numerics tier:** the 2.4e-4 composed-loop drift (vs ~1.5e-6 in
  Debug) is FMA/rounding change in the release-optimized VM feeding back
  through the KF's recurrent Riccati recursion. It stays within the 1e-3
  solver-accuracy tier but exceeds the Debug oracle's 1e-4 threshold — release
  .so oracle tests need the looser tier.
- `runtime/build.zig` now ships `.strip = optimize != .Debug` (release builds
  drop the ~3 MB of DWARF; Debug keeps it — the debug info is useful for field
  backtraces, so Debug stays unstripped), re-added `"stripped": bool` to the
  build manifest, and the header comment documents ReleaseFast as the only
  production mode.

**Deployment story for small robot targets** (verified): cross-compiling is a
single flag — `zig build -Dtarget=aarch64-linux-gnu` produced a working ARM64
`.so` with no sysroot (4.9 MB Debug; release ≈500 KB). One robot = one
controller = one binary: graph + baked solver compiled in, no malloc, fixed
stack buffers, f64. RAM footprint is dominated by the solver's static data
(~0.5–0.7 MB) — Pi-class OK, freestanding MCU possible later.

**Verification:** `make test-zig` 15/15 (Debug default); one-tick smoke +
100-tick oracle on stripped ReleaseFast pass; manifest records
`optimize`/`stripped` correctly for all three modes.
