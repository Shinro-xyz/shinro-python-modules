### 2026-08-10 17:00 UTC — configurable linearization point for CartPole & InvertedPendulum

**What:** `get_model()` on `CartPole` and `InvertedPendulum` now linearizes about a
user-specified operating point `(x0, u0)` instead of being hard-coded to the
upright equilibrium.

**Why:** The closed-form Jacobians previously returned were only valid around
the origin (upright). Controllers/estimators want linear models about arbitrary
operating points (e.g., pendulum near-horizontal, cartpole off-upright).

**How:**
- `get_model(self, x0=None, u0=None, eps=1e-6)` delegates to the existing
  `shinro.utils.linearization.linearize()` helper (central finite differences)
  on the plant's `self.dynamics`. Omitting `x0`/`u0` defaults to the upright
  equilibrium with zero control, preserving backward compatibility — the
  no-arg return value matches the previous closed-form matrices.
- `linearize()` passes numpy arrays to `f` regardless of backend, so each plant
  got a private `_dynamics_np(x, u)` wrapper that converts numpy → backend via
  `self.bk.from_numpy`, runs `dynamics`, and converts back with
  `self.bk.to_numpy`. This keeps NumpyBackend and TorchBackend both working.
- Class docstrings updated: the linearization point is now configurable; the
  analytic Jacobian block still documents the upright default.

**Design decisions:**
- Backward-compatible default (no-arg `get_model()` unchanged) rather than a
  breaking required-arg API — all existing callers (`batched_adapter`,
  `scenario_factory`, `components`, `scenario_runner`) keep working.
- Always route through `linearize()` (even at upright) for a single code path,
  per user preference, accepting finite-difference error (~1e-8) over the
  previously exact closed form. Docstrings note the upright Jacobians remain
  the documented default.
- Applied to both plants for consistency (InvertedPendulum had the same
  hard-coded pattern).

**Tests:** 6 new tests in `tests/test_plants.py` (3 per plant):
- upright model matches the analytic closed-form Jacobians (atol 1e-6)
- no-arg `get_model()` ≡ explicit `get_model(zeros, zeros)` (atol 1e-12)
- non-upright point produces an A distinct from the upright A

**Verify:** full suite `pytest tests/` → 808 passed, 5 skipped; `ruff check`
clean on edited files. `ruff format --check` flags pre-existing style in these
files (single quotes, multiline arrays) unrelated to this change — left
untouched to keep the diff minimal. Note: `plants/double_pendulum.py` had
pre-existing uncommitted changes in the working tree, not part of this work.

### 2026-08-10 21:00 UTC — extract numpy bridge + linearize_plant helpers, add Plant.input_dim

**What:** Promoted the duplicated `_dynamics_np` wrapper into reusable utils and
made `linearize_plant`'s default control dimension correct for multi-input
plants.

**Why:** The `_dynamics_np` bridge (numpy ↔ backend conversion so `linearize()`
can call a backend-native `dynamics`) was copy-pasted into CartPole and
InvertedPendulum. Every future nonlinear plant would need the same boilerplate.
Separately, a hardcoded `zeros(1)` default for `u0` is wrong for any plant with
multi-dim control (DoublePendulum=2, future Quadrotor=4, ArmRobot twist=6) and
would silently produce a wrong-shaped `(n_x, 1)` B.

**How:**
- `src/shinro/utils/linearization.py`:
  - `as_numpy_f(f, backend)` — wraps any backend-bound `f(x, u)` into a
    numpy-in/numpy-out callable via `backend.from_numpy`/`to_numpy`.
  - `linearize_plant(plant, x0=None, u0=None, eps=1e-6)` — resolves `x0`
    default from `len(plant.get_state())`, `u0` default from
    `plant.input_dim`, bridges `plant.dynamics` through `as_numpy_f`, and
    delegates to `linearize`.
- `src/shinro/components.py`: added optional class attribute
  `Plant.input_dim: int | None = None` (not abstract — no subclass breaks).
  `linearize_plant` raises `ValueError` if `input_dim` is unset and `u0` is
  not passed, so a multi-input plant can never silently get a wrong-dim `u0`.
- `src/shinro/plants/cartpole.py` / `inverted_pendulum.py`: removed the
  duplicate `_dynamics_np` method and the now-unused `import numpy as np`;
  `get_model` is a one-liner `return linearize_plant(self, x0, u0, eps=eps)`;
  `__init__` sets `self.input_dim = 1`.

**Design decisions:**
- `input_dim` is an optional attribute, not a new abstractmethod — plants that
  don't use `linearize_plant` (ArmRobot, HolonomicMobileRobot, Quadrotor) are
  untouched. They opt in with one line when they need it.
- Safe-error over silent-wrong: `ValueError` when the control dim can't be
  inferred, rather than defaulting to `zeros(1)`.
- `scenario_factory.py` still derives `n_u` from `B.shape[1]`; reading
  `plant.input_dim` there is a possible future cleanup, out of scope.

**Tests:** 10 new tests in `tests/test_linearization.py`:
- `TestAsNumpyF`: numpy-backend passthrough; torch-backend round-trip.
- `TestLinearizePlant`: cartpole upright matches analytic Jacobians (atol
  1e-6); defaults ≡ explicit zeros (atol 1e-12); raises `ValueError` when
  `input_dim` unset and `u0` not passed; `u0` defaults to `zeros(input_dim)`
  with B shape `(state_dim, input_dim)` for a 3-dim stub plant.

**Verify:** full suite `pytest tests/` → 818 passed, 5 skipped (10 new);
`ruff check` clean on all edited files.

**Note:** `double_pendulum.py` is being worked through separately by the user
(no changes made here). It will adopt `input_dim = 2` and, once it gains a
backend, `linearize_plant`.

**Why:** The previous file was a non-instantiable stub — it missed the abstract
`physics_engine` method, had no `self.bk`, and contained three runtime bugs
(out-of-bounds gravity indexing, a `np.array(x, y)` TypeError, and a `step()`

**How:**

  - `__init__(mass_top, mass_bottom, length_top, length_bottom, dt, g,

  - Fixed `_make_gravity_vector` indexing (`G[0,0]`/`G[1,0]`, G is 1-D now),
    fixed `np.array([...])` typo, and rewrote `step` as semi-implicit Euler
    (`omega_new = omega + thetaddot*dt; theta_new = theta + omega_new*dt`).
  - `get_model` → `linearize_plant(self, x0, u0, eps)` one-liner (reuses the
    util extracted earlier today).
  - `physics_engine` attach/detach + engine-branch `get_state` (reads
    `hinge_1`/`hinge_2` qpos/qvel) and `step` (writes `torque_1`/`torque_2`).
  - `from_config` parses all fields incl. `state_bounds` and optional `engine`

  - `@register_plant_detector("DoublePendulum")` matches exactly 2 hinge

- `models/double_pendulum.xml` (new MJCF): 2 hinge joints + 2 motors, radian

### 2026-08-10 23:00 UTC — review of DoublePendulum port: Coriolis bug + convention fixes

**What:** Post-port review of `src/shinro/plants/double_pendulum.py` caught a
latent math bug inherited from the original user code, plus convention and
hygiene issues. Fixed all four.

**Findings & fixes:**
1. **Coriolis matrix bug** (the important one). The original set
   `C[0,0] = m2 l1 l2 sin(Δθ) ω2` and `C[0,1] = C[0,0]`, which makes
   `C @ ω` row 0 = `m2 l1 l2 sin(Δθ) ω2 (ω1 + ω2)` — a spurious `ω1·ω2`
   cross-term not present in the Euler-Lagrange velocity terms. The correct
   E-L velocity-squared terms are `+m2 l1 l2 sin(Δθ) ω2²` (eq 1) and
   `-m2 l1 l2 sin(Δθ) ω1²` (eq 2), which require `C[0,0]=0`,
   `C[0,1]=m2 l1 l2 sin(Δθ) ω2`, `C[1,0]=-m2 l1 l2 sin(Δθ) ω1`, `C[1,1]=0`.
   Fix: leave `C[0,0]` at 0 (from `zeros`), set `C[0,1]` directly. None of the
   original tests caught this because they all used `ω=0`, where `C ω = 0`.
2. **Docstring convention.** Class said "angle from upright" but the dynamics
   (`+sin(θ)` gravity, stable equilibrium at θ=0) is the **downward/hanging**
   convention. Fixed to "angle from the downward vertical; rest equilibrium
   θ=0 is stable (hanging down)."
3. **MJCF orientation.** `models/double_pendulum.xml` had links pointing
   **up** (+z), making MuJoCo qpos=0 the inverted (unstable) pose —
   inconsistent with the analytical model's hanging-down rest. Flipped all
   geoms/body positions to -z so qpos=0 = hanging down = analytical rest.
4. **Torch UserWarning.** `dynamics` did `self.bk.array(tau)` on an
   already-backend tensor, triggering "To copy construct from a tensor"
   warnings (10 per suite run). Removed the redundant re-wrap; `tau` is
   already a backend array when `control` has `__len__`.

**New test:** `test_dynamics_coriolis_matches_closed_form` in
`TestDoublePendulum` — sets `g=0, τ=0` so only the Coriolis term contributes,
uses nonzero `ω = [1.5, -0.7]`, and asserts `θ̈ = -M⁻¹ C ω` against the
closed-form `[m2 l1 l2 sin(Δθ) ω2², -m2 l1 l2 sin(Δθ) ω1²]` (atol 1e-9).
This would have failed against the old C matrix and pins the fix.

**Verify:** `pytest tests/` → 849 passed, 5 skipped (1 new test, ×2 for
numpy/torch = 2); `make lint` clean. The 10 torch UserWarnings are gone.

**Note:** The Coriolis bug was inherited from the user's original draft, not
introduced by the port. The port faithfully preserved it; this review caught
it by deriving the E-L equations by hand. Lesson: tests at `ω=0` can't
validate the velocity-dependent terms — a moving-state test is essential for
any plant with a Coriolis/centrifugal term.
