# 2026-09-24 — Fused `layernorm` op (kernel + six-surface wiring + ONNX importer)

Branch: `feat/nn-kernel-support`

## Why

The recurring "next" item from the recurrent-policy work: `LayerNormalization`
is the one non-`Conv` op standing between the wcompton G1-humanoid GRU policy
(`wcompton/legged_locomotion_rl`) and an import. It is also the natural sibling
of the existing fused `softmax`/`gelu`/`elu` ops — a per-row reduction over the
last axis with two feature-length operands. Following the fused-op precedent
(`gemm`, the recurrent cells), it becomes **one** kernel/node rather than the
~6-node `mean → sub → pow → mean → add → rsqrt → mul → mul → add`
decomposition, which would materialize several full copies of the activation.

## What changed

`src/shinro/runtime/linalg.zig` — `layernorm_rows(rows, cols, a, scale, bias, comptime eps) -> [rows*cols]`,
treating the flat row-major buffer as `(samples, features)`: per row
`mean = Σa/cols`, biased `var = Σ(a-mean)²/cols`, `rstd = 1/sqrt(var+eps)`, then
`out = (a - mean) * rstd * scale + bias`. `scale`/`bias` are the ONNX
`Scale`/`B` feature vectors, fused into the same kernel (no separate `mul`/`add`
nodes). `eps` is a **comptime** parameter, so the whole kernel constant-folds
per node. This is the canonical torch `nn.LayerNorm` form: biased variance
(divide by `cols`), `eps` under the square root. Header doc comment states the
exact arithmetic contract (the three-way oracle needs the *same* expression in
the *same* order, not merely the same mathematics).

**Bug caught in review.** The first version had `return out;` *inside* the row
loop, so it returned after row 0 and left rows `1..n` `undefined`. That is the
worst failure shape: silently correct for any single-row (`vec`) input, garbage
otherwise, no error. Moved the `return` below the loop and added a two-row unit
test explicitly as the regression guard. (Also renamed to `_rows`, matching the
`softmax_rows` convention, and cleaned a trailing-whitespace line.)

## Key decision: `eps` is baked, not an input port

`LayerNormalization`'s `epsilon` is an **attribute** — a model constant frozen
at export. It rides the same mechanism as `elu`'s `alpha`: an `f64` cannot live
in the node's single `aux: usize`, so `lower_zig.py` bakes it into a parallel
`layernorm_eps: [f64]` table and stores the table index in `aux`. Making it a
C-ABI **input port** was the alternative and was rejected: ports are for values
that change per call (state, MPPI's `epsilon` noise, SMC's `f_x`/`g_x`), and a
port would force the host to repack the same constant every tick forever while
muddying the manifest. Attribute-in ⇒ compile-time-baked is the consistent rule
(elu alpha, gemm alpha/beta, gru `linear_before_reset`).

## Wiring (all six surfaces)

- **`ops.py`** — `layernorm` numpy handler (the correctness oracle for
  `interpret`, the importer's eager evaluation, and the `.so`). Uses the
  identical reciprocal-then-multiply order as the kernel.
- **`trace_backend.py`** — `TraceBackend.layernorm(x, scale, bias, *, eps=1e-5)`,
  shape-preserving (like `softmax`).
- **`lower_zig.py`** — enum variant, `layernorm_eps` table + `layernorm_aux`
  map (the `elu_alpha` pattern), threaded through `_node_line` /
  `_graph_manifest` / `_node_vm_info` (the single source of truth for
  `(vm_op, aux)`, which the drift guard cross-checks).
- **`lower.zig`** — VM arm next to `.elu`; operands via `node_input` +
  `node_input_at` (the `gemm` multi-operand shape); a `comptime { … @compileError }`
  gate that `scale`/`bias` are exactly the `(cols,)` feature vector; `1-D`
  handled the `softmax` way (`rows=n, cols=1, vec=true` ⇒
  `layernorm_rows(1, n)`, never `n` rows of length 1).
- **`onnx_import.py`** — `LayerNormalization` added to `_SUPPORTED_OPS` and an
  `emit_layernorm` translator: last-axis only (same axis rule as `Softmax`), a
  missing optional `B` emitted as an explicit **zero feature-vector** (the
  comptime gate needs one entry per feature, so a scalar won't do), and loud
  rejects for a non-last `axis` and `stash_type != 1`.
- **tests** — Zig unit tests (multi-row, scale/bias, eps floor), a `.so` oracle
  graph (2-D multi-row, 1-D single-row, non-default `eps`) diffed against both
  `interpret()` and an independently written numpy reference, op-shape-matrix
  cells (`layernorm_2d`, `layernorm_2d_eps`, `layernorm_1d`), and four importer
  tests (scale+bias, missing-bias-as-zeros, non-last-axis reject, `stash_type`
  reject).

## Follow-up — conditioning + operand-shape coverage

The initial test set was narrow in two ways: every case was ≤5 features, and all
operands were the 1-D `(cols,)` form. Both were closed.

- **Width-128 large-offset cell** (`.so` oracle). `ln128` normalizes a
  128-feature row fed as `x = 1e9 + (arange(128) - 63.5) + N(0, 0.5)` — a large
  offset with an O(1) spread, the condition-number regime where the one-pass
  `E[x²] − mean²` variance loses ~9 significant digits. Measured over 20 feeds:
  `|.so − interpret|` and `|.so − two-pass reference|` both **3.4e-08**, while
  `|.so − naive one-pass|` is **4.0e-01** (~1.2e7×). The cell is deliberately
  *not* compared at bit-parity — the f64 mean of ~1e9-magnitude values is itself
  only good to ~1e-6, so the tolerance is `atol=1e-4` and the load-bearing
  assertion is the two-pass-vs-naive gap (`err_two < 1e-4`, `err_naive > 1e-2`,
  `err_two < 0.05·err_naive`). That gap *is* the anti-cancellation property.
- **`(1, cols)` operand cell** (`layernorm_2d_row_operands` in the shape
  matrix) pins that the VM comptime gate accepts any operand with
  `rows*cols == cols` and that the kernel indexes the flat buffer by feature,
  not by rank.

Re-verified: `make lint` clean; `test_zig_lowering` + `test_op_shape_matrix` →
**97 passed, 2 skipped** (the two pre-existing `sign` skips).

## Perf — const nodes are no longer copied into the workspace

Branch: `feat/nn-kernel-support`. Separately from layernorm, investigated the
NN-kernel perf gap on the Pi. The first thing the measurement found was not a
naive loop — it was a redundant weights memcpy.

### Why

The VM's `.cst` arm copied every baked constant out of `g.const_blob` into its
workspace slot on **every tick**, and consumers read it back out of the
workspace. For a control graph the constants are a few KiB (cartpole LQR+KF:
188 f64 = 1.5 KB), so this was invisible and had never been measured with an
MLP-sized constant. For an ONNX policy the constants *are* the workspace —
microduck: `const_blob_bytes` 1,583,184 of `buf_bytes` 1,599,544 — so each tick
did a full **1.58 MB weights memcpy** (read + write, zero flops) *before* the
kernel read the same weights again.

It wasn't a deliberate decision: the VM gives every node a workspace slot (the
offset table is uniform) and every input is read from the workspace (uniform
`node_input_at`), and those two choices together force a const node to
materialize its value into its slot. Correct and simple for kilobyte constants;
wrong at megabyte scale.

### What changed

`src/shinro/runtime/lower.zig`, two spots:

- `.cst` becomes a no-op (it no longer writes its slot).
- `node_input_at` special-cases a `.cst` source and returns the `const_blob`
  slice directly; every other node keeps the workspace contract unchanged.

The conditional is free — the op is a comptime constant in the unrolled node
loop, so each consumer compiles to either a blob read or a workspace read. The
values are **bit-identical** (same bytes, just not copied), so no oracle
tolerance moved. The const workspace slots still exist (offset table unchanged);
removing them is a separate, perf-neutral cleanup.

### Measured (Pi 3 B+, bare kernel, 100k ticks, CLOCK_MONOTONIC_RAW)

| policy | const blob | before (median) | after (median) | speedup | 1 kHz |
| --- | --- | --- | --- | --- | --- |
| microduck | 1.58 MB | 2973.4 µs | **1527.3 µs** | **1.95×** | 336→655 Hz, still misses |
| go2 | 1.52 MB | 2773.0 µs | **1406.3 µs** | **1.97×** | 711 Hz, misses |
| drone_gru | 0.71 MB | 1293.4 µs | **653.3 µs** | **1.98×** | **1531 Hz, 0% miss** |
| toy_lstm | 1.3 kB | 22.60 µs | 22.76 µs | 1.00× | unchanged |

microduck WCET 10961 → 2081 µs. The uniform ~2× on weight-carrying policies and
unchanged small-const toy_lstm is the signature of removing a redundant full
memcpy.

**Classical controls are unaffected** — same-session A/B on cartpole LQR+KF
(300k ticks): before median 21.875 µs / mean 22.26, after 22.396 / 22.76, p99
flat, WCET 425→405. A ~3 KB copy is sub-µs and cache-resident; the effect is
noise. Confirms the earlier finding that classical kernels are not memory-bound
(they sit at ~20 µs with 0 misses).

### Where the time goes now

The tick now scales linearly with const size (1.58 MB→1527 µs, 0.71 MB→653 µs,
both ≈ **1.05 GB/s**), and a `memmove` probe on the Pi costs 1285 µs for 1.58 MB
(2.46 GB/s r+w). So the remainder is dominated by *streaming the weights from
DRAM*, not by the scalar reduction loops. **SIMD compute would not be the next
lever** — fewer weight bytes would be. Verified 100.0000% of the microduck/go2
const elements are f32-exact (their ONNX initializers are float32), so an f32
const blob with widen-on-read would be bit-identical and halve the dominant
traffic. Not implemented yet — a separate decision.

## Perf — SIMD f64 gemm (and the f32 negative result)

Same branch/session. After const-aliasing (above) the NN path was still ~2× off
where it should be, so the bottleneck was measured directly with two
experiments: one on the data type, one on the compute.

### f32 weights — correct but *slower* (reverted at the time)

Hypothesis: the policy kernel is DRAM-bandwidth-bound, so storing weights as f32
(half the bytes) should approach 2×. Implemented as a mixed-dtype `gemm`
(comptime operand type, widen-on-read in a register, f64 accumulate), a separate
`const_blob_f32` for f32-exact gemm weights, a `cst_f32` op, and an f32 round-trip
check at lower time.

Result — **the hypothesis was wrong**:

| policy | f64 weights | f32 weights | delta |
| --- | --- | --- | --- |
| microduck | 1527.3 µs | 1868.2 / 1869.1 µs | **+22%** |
| go2 | 1406.3 µs | 1680.4 µs | **+19%** |

Correctness was fine (on-Pi fidelity `max|err| 2.331e-15`; `.so` halved to
804,664 B), so it was purely a perf loss. The tell: the delta is **+341 µs** and
197,896 weights × **1.72 ns** = **340 µs** — the `@floatCast` cost almost exactly
the regression, and the halved DRAM traffic saved ~zero. So the kernel is **not
bandwidth-bound**; the weight loads are prefetched/overlapped behind the compute
and the bottleneck is the **serial f64 accumulation chain** (`s += a*b`, which
Zig's strict FP forbids reassociating). Adding a conversion to a compute-bound
inner loop only adds work. Reverted at the time — and re-applied below, once
SIMD changed the calculus.

### f32 weights, revisited after SIMD — now a win

After the SIMD reduction landed, the f32 blob was re-applied on top of it (same
`cst_f32` op + `const_blob_f32`, but the widening now happens **per vector lane**
inside `dot`: one `@floatCast` per `SIMD_VL` elements, not per element) — and it
flipped:

| policy | f64 SIMD | f32 SIMD | gain |
| --- | --- | --- | --- |
| microduck | 823.9 µs | **752.9 µs** | 1.09× |
| go2 | 784.7 µs | **718.2 µs** | 1.09× |
| drone_gru | 373.5 µs | 370.3 µs | 1.01× |

Two reasons it flipped: (1) the conversion is now **one vector convert per VL
lanes**, not one scalar convert per element — a host smoke test of the raw dot
showed f64 0.26 s vs f32-weights 0.25 s, i.e. effectively free; and (2) after
SIMD the compute halved, so the weight stream is a larger share of the tick, and
it is halved. The weights *are* the ONNX float32 initializers, so the result is
unchanged — on-Pi fidelity **9.992e-16** (PASS) — and `.so` halves again to
805,992 B. `drone_gru` barely moves because only its 2 gemm head weights are
covered; the GRU cell's W/R are contracted through `matvec` inside the cell
kernel — the next extension.

Implementation note: the weight element type is a single explicit
`comptime TB: type` on `dot`/`gemm`, chosen by the VM from the source node's op
(`.cst_f32` vs `.cst`) — no `anytype`, and call sites whose operand is always f64
(matvec, the unit tests) state `f64` at the call.

### SIMD in the reduction — the actual lever (kept)

`linalg.zig` gets a `dot()` helper: accumulate into a `@Vector(SIMD_VL, f64)`
(NEON = 2 lanes, AVX = 4) with `@mulAdd` (fused multiply-add), one horizontal
`@reduce(.Add)` at the end, scalar tail for `len % VL`. This splits the serial
chain into `VL` independent ones — exactly what the f32 result said was needed.
`gemm`'s **transB** path (both operands contiguous — the torch/ONNX layout every
policy uses) routes through it; the non-transB strided path stays scalar. A
`SIMD_MIN_K = 2 * SIMD_VL` gate keeps small (classical-sized) contractions on the
exact scalar order, so the control path and small-matrix tests are unchanged.

The only numerical change is the regrouped summation: relative ~1e-15, and the
on-Pi fidelity oracle confirms **9.992e-16** (tol 1e-12, PASS).

| policy | original | + const-alias | + SIMD gemm | total | 1 kHz |
| --- | --- | --- | --- | --- | --- |
| microduck | 2973.4 µs | 1527.3 | **823.9 µs** | **3.6×** | 100% miss → 0.58% (1214 Hz) |
| go2 | 2773.0 µs | 1406.3 | **784.7 µs** | **3.5×** | 0.52% (1274 Hz) |
| drone_gru | 1293.4 µs | 653.3 | **596.0 µs** | **2.2×** | 0% (1678 Hz) |

`drone_gru`'s small gain (1.10×) is the diagnosis for the next lever: it is
mostly the **GRU cell**, whose contraction goes through `matvec` (not gemm), so
it was not vectorized.

### Follow-up — SIMD in `matvec` (the recurrent cells)

`matvec` now routes each row through `dot` too (row `i` of `a` and all of `v`
are contiguous along the contraction) — that is the cells' `x·Wᵀ` / `h·Rᵀ`.
`vecmat` and `matmul` stay scalar: their contraction walks a column (stride `n`),
so it is not contiguous. The SIMD floor is now a fixed `SIMD_MIN_K = max(2·VL, 8)`,
so the small path is scalar on *every* target — a result never depends on the
build target's SIMD width.

| policy | original | +const-alias | +gemm SIMD | +matvec SIMD | total |
| --- | --- | --- | --- | --- | --- |
| drone_gru | 1293.4 µs | 653.3 | 596.0 | **373.5 µs** | **3.46×** |
| bulletdodge_lstm | 3994.1 µs | — | — | **1177.7 µs** | **3.39×** |
| toy_lstm | 22.6 µs | 22.8 | 22.8 | 23.0 µs | 1.0× |

drone_gru is now **2677 Hz / 0% miss**; bulletdodge_lstm **849 Hz** (still over
the 1 kHz deadline, but 3.4× down from 100% miss). On-Pi fidelity:
drone_gru 1.110e-15, bulletdodge_lstm 5.107e-15 (both PASS at 1e-12).

### Follow-up — f32 for the cells, and no dead const slots

Two follow-ups on top of the f32 blob.

**(b1) The recurrent cells' weights are f32 too.** The blob only covered `gemm`
weight operands, which is why `drone_gru` barely moved — its GRU cell contracts
W/R through `matvec` (whose weight operand is `a`, not a gemm `b`).
`_is_f32_weight` now also accepts a cell's W/R (input positions 1/2), and
`matvec` + `lstm_cell`/`gru_cell`/`rnn_cell` take the same `comptime TB`. A cell
reads W and R from the same blob, so a coherence pass keeps them together — if
only one is f32-eligible, both stay f64 (otherwise one side would be read from
the wrong blob). The cell bias B stays f64 (it is tiny).

**(b2) Const nodes no longer own a workspace slot.** They are read from the baked
blob, never the workspace, so `buf_len` now sums only the nodes that use it and
`shinro_step` skips const nodes entirely (no slice at an unused offset). This is
perf-neutral — the slots were never touched — but the manifest is now honest:

| policy | buf_bytes before | after |
| --- | --- | --- |
| microduck | 1,599,544 | **16,360** |
| drone_gru | 715,136 | **6,592** |
| bulletdodge_lstm | 2,152,000 | **24,936** |

The workspace is now the real working set (~6–25 kB, L1/L2-resident) instead of
being ~98% dead weight storage.

Measured on the Pi (bare kernel, 100k ticks):

| policy | after f32-gemm | after b1+b2 | gain |
| --- | --- | --- | --- |
| microduck | 752.9 µs | 749.7 µs | — (noise) |
| go2 | 718.2 µs | 717.0 µs | — (noise) |
| drone_gru | 370.3 µs | **352.3 µs** | 1.05× |
| bulletdodge_lstm | 1177.7 µs | **1134.2 µs** | 1.04× |
| toy_lstm | 23.0 µs | 22.6 µs | — (1.3 kB consts) |

Fidelity is unchanged (`drone_gru` 1.110e-15, `bulletdodge_lstm` 5.107e-15,
microduck 9.992e-16 — all PASS): the cell weights are the same ONNX float32
values, and b2 only moves offsets. The manifest test that asserted "every node
owns a contiguous slot" was updated to the new contract — const nodes sit at the
current end and do not advance it.

### Head-to-head vs onnxruntime (measured on the Pi)

The historical bench figure (2026-09-22) was "ORT ~4.7× faster on the same
board". Measured directly this session with onnxruntime 1.30.0 on the Pi 3 B+,
same `CLOCK_MONOTONIC_RAW` clock + 2000-tick warmup as the shinro harness
(`measure_ort_timing.py`, input seeded identically):

| policy | shinro original | shinro now | ORT (f32) 1-thr | ORT default | gap before | gap now |
| --- | --- | --- | --- | --- | --- | --- |
| microduck | 2960 µs | 823.9 µs | 651.4 µs | 657.4 µs | 4.55× | **1.27×** |
| go2 | 2773 µs | 784.7 µs | 635.2 µs | 647.2 µs | 4.37× | **1.24×** |

With the f32 weight blob on top (above), those gaps tighten further: microduck
752.9 µs → **1.13×**, go2 718.2 µs → **1.12×**.

ORT threading does **not** help (651 vs 657; 635 vs 647) — these per-call
workloads are too small — so the single-thread comparison is the fair one. The
remaining ~1.25× is almost exactly the f32 factor: ORT computes in f32 (4 NEON
lanes per register) while the kernel stays f64 (2 lanes). Closing it means f32
*compute*, which changes results and needs its own tolerance tier — a decision,
not a free win. Otherwise the kernel is now within ~1.25× of a tuned f32 SIMD
runtime, at f64, in a 1.6 MB dependency-free `.so` vs ORT's 24 MB
`libonnxruntime`.

## ONNX op-coverage scan — which ops actually block real policies

**Question.** The importer's gaps had been guessed at twice and guessed wrong at
least once, so the roadmap was made data-driven: *which ONNX ops block real
robotics-RL policies?*

**Method.** Downloaded the **graph structure** of 31 ONNX policies from 6
robotics-RL HF repos — the ones the 2026-09-23 survey identified — and diffed
`op_type` histograms against the importer's `_SUPPORTED_OPS`. Weights are not
needed for this, so no `.data` sidecars were fetched.

Corpus: `xiaofengzi/microduck-walking-onnx`, `diasAiMaster/unitree-go2-velocity-flat`,
`astralhf/eco-drone-policies` (3), `code3939/DecisionTransformer-Unity-Sim` (sampled 8),
`wcompton/legged_locomotion_rl` (sampled 14, the G1 humanoid),
`cm107/agv-demo` (4).

**Headline: 31 models, 4 803 nodes, 16/31 import as-is.**

**Correction.** The shape/plumbing ops (`Shape`, `Cast`, `Squeeze`, `Unsqueeze`,

dominate PyTorch exports (`Constant` 1301, `Unsqueeze` 546, `Reshape` 359,
`Concat` 296, `Transpose` 271, `Shape` 239, `Gather` 234), which is exactly why
half the corpus imports. The top blocker is **`Slice`, not `LeakyRelu`.**

### Implementation notes (cheap → real)

- **`ArgMax`** → the VM already has an `argmax` op; this is an *importer mapping*
  only, no kernel.
- **`LeakyRelu`, `Sqrt`, `Log`, `Mod`** → elementwise kernels, the `elu` pattern
  (comptime scalar + the `elu_alpha` table for the slope). Trivial.
- **`Trilu`, `Equal`, `Expand`, `Where`** → these are attention **mask
  construction at known shapes**, so most of it is constant-foldable at import;
  `Where` already maps to the VM's `where_op`. The 1/√d scaling is `Sqrt` on a
  const, also foldable.
- **`Multinomial`** → host-side, exactly like `RandomNormal`: becomes an input
  port and the *host* samples. That is the standing doctrine ("the binary does
  raw maths; the host owns sampling").
- **`Slice`** → belongs to the shape-glue family (`start`/`end`/`axes`/`steps`
  are attributes or consts).
- **`Conv`** → the one genuinely new kernel (a stencil, not a contraction — the
  `dot`-based work does not transfer). Note *where* it appears: `g1_conv`
  (230 nodes, `Conv`×6 + `LayerNorm` + `Softmax`) and `agv` (`Conv`×8) — i.e.
  the **perception** encoder, consistent with "CNN/transformer = perception
  layer, MLP/RNN = action layer".

### Reading the corpus (architecture, not just ops)

The deployable *action* layers are MLPs and RNNs, as expected:

- `go2`: `Gemm`×4 + `Elu`×3 + `Sub`/`Div` — the RSL-RL actor.
- G1 `blind_flat_end2end` / `depth_flat_mlp_end2end` (12 of the 14 sampled):
  **`Gemm`×5 + `Elu`×4** — plain MLPs, and all importable today.
- `eco-drone policy_fw`: `GRU`×1 + `Gemm`×2 + `Relu` + shape-glue — a recurrent
  policy, importable today.
- The `Conv`/attention policies are the `depth_*`, transformer, and AGV ones.

## ONNX `Slice` + `ArgMax` importer support

Branch: `feat/nn-kernel-support`. Picked up the first two entries of the scan's
recommended order. **No VM/kernel change** — both ops lower onto machinery that
already exists (`slice`, `gather`, `argmax`, `reshape`); this is all importer
work in `src/shinro/codegen/onnx_import.py`.

### Design

**`Slice`** is handled in the shape-glue path in two tiers:

- **Constant data folds to a `const`** — arbitrary axes, steps, and negative
  bounds. This is the real-world use: a `torch.nn.GRU` export does not pass its
  gate weight straight through, it `Slice`s `gru.weight_ih_l0` into three
  `(H, I)` blocks and `Concat`s them in ONNX gate order (torch `(r,z,n)` →
  ONNX `(z,r,n)`). Because the operand is an initializer, the whole
  Slice→Concat→Unsqueeze chain folds at import into one constant.
- **Runtime data must be a single step-1 axis range on a rank ≤ 2 operand.**
  Axis 0 becomes the VM's `slice` (the existing contiguous flat/row offset);
  axis 1 becomes a `gather` with a baked `arange` index (reusing `gather_cols`
  rather than adding a kernel). Full slices are a no-op. Everything else —
  multi-axis, stepped, rank-3, non-constant `starts`/`ends` — is rejected
  loudly.

The const fold deliberately uses **raw numpy indexing** (`data[tuple(slices)]`),
which is literally the ONNX reference implementation. An early attempt
normalized bounds through `slice.indices(dim)` first; that diverges from ONNX
for the sentinel bounds (`end = INT64_MAX` with a negative step → Python clamps
to `dim-1` and yields empty, and the reference yields empty too). Runtime
normalization *does* use `slice.indices`, but only for positive step-1, where
the two agree.

**`ArgMax`** maps onto the VM's whole-tensor `argmax`, so the reduction axis
must be the only non-singleton dimension (a 1-D logits vector, or the
batch-1 `(1, n)` block of an ML-Agents policy). `keepdims` is honored by
reshaping the scalar index to the ONNX output shape; `select_last_index=1` is
rejected because the kernel resolves ties to the first index, like numpy. A
genuine per-axis reduction (e.g. `(2, n)` axis 1) would need a new kernel and is
rejected with that message.

**Recurrent weights may now be produced constants.** `_cell_weight` used to
require `self.initializers[name]`. But once Slice/Concat folds the gate reorder
to a constant, the recurrent op's `W` is a *node-produced* constant, not an
initializer name. `_cell_weight` now resolves it through the importer's tensor
map and requires that node to be a `const`. This is what makes the torch-GRU
pattern actually importable; a new synthetic fixture mirrors the exact idiom.

### Honest correction to the scan's "models blocked"

The op *histogram* overcounts blocked models, because it ignores reachability
and graph structure:

- `BulletDodge` was already importable — its `Slice`s feed the LSTM's
  `initial_h`/`initial_c`, and those slots are intercepted as fresh state ports,
  so the Slice nodes are unreachable from the action and never translated.
- `dt_model_12` is a four-input sequence model (`observations`, `actions`,
  `returns_to_go`, `timesteps`) and needs `Sqrt`; Slice does not unlock it.
- `AGVAgent` needs `Conv`/`LeakyRelu`/`Log`/`Multinomial`, so `ArgMax` alone
  does not unlock it.

The genuinely unlocked model is `eco-drone policy_rover_v2` (the torch GRU gate
reorder), and only because of the `_cell_weight` change. The large corpus
models were fetched **structure-only** (no `.data` sidecars), so a full
end-to-end `import_onnx_policy` of `policy_rover_v2` could not be re-verified
here; the produced-weight path is covered by the synthetic fixture instead.
