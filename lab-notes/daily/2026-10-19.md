# 2026-10-19 — Split the MCP server into per-domain modules

Branch: `refactor/mcp-server-split`

## Why

Two questions came up, in order:

1. **Does the MCP server belong in this repo at all, or in its own repo?**
   Answer: keep it here. `src/shinro/mcp/server.py` imported only the public
   factory surface (`ControllerFactory`, `EstimatorFactory`,
   `TrajectoryFactory`, the registries, `NumpyBackend`/`TorchBackend`,
   `LTISystemsAnalyzer`) — nothing in core imports *from* `mcp/`, so it is a
   facade over the library, not a subsystem. The decisive argument is the tool
   surface: `list_controller_types()` / `list_estimator_types()` /
   `list_trajectory_types()` just dump the registries, so any component added
   to shinro shows up in the MCP tools for free. A separate repo would need a
   coordinated release per component and would drift. It would only earn its
   own repo if it grew past a facade (remote transport, auth, hosting) — that
   is an infrastructure concern, not a client-library feature.
2. **The file itself was the problem:** 785 lines holding four tool families
   plus shared helpers, and the four sections were already marked with banner
   comments — i.e. the split was latent in the file.

## Change

`src/shinro/mcp/` split by domain, with **zero logic changes** — every tool
body was moved verbatim (sliced from the original by section anchor, not
retyped):

| Module | Lines | Contents |
|--------|-------|----------|
| `_common.py` | 63 | `server` (the single `FastMCP` instance), `_store`, `_resolve_backend`, `_to_list`, `_from_list`, `_set_mpc_default_constraints`, `_make_analyzer` |
| `_controllers.py` | 218 | create / compute / reset, MPC constraints, PID limits, listing (8 tools) |
| `_estimators.py` | 106 | create / estimate / reset, listing (5 tools) |
| `_trajectories.py` | 159 | create / generate / position_at, listing (5 tools) |
| `_analysis.py` | 270 | controllability, observability, 3× Gramians, summary, balanced truncation (7 tools) |
| `server.py` | 103 | imports the tool modules for registration, re-exports every tool + `_store`, `main()` |

**The load-bearing constraint — one store, one server.** `_store` and `server`
must be the *same objects* everywhere, or the tests' `clear_store` fixture
would clear a different dict than the tools read, and tools would register
against a stray `FastMCP`. They are defined once in `_common.py` and imported
(never re-created) by the tool modules; `server.py` re-exports the same names.
Pinned by an identity assertion during development (`server is
_common.server`, `_store is _common._store`).

**The second constraint — import compatibility.** `tests/test_mcp_server.py`
imports 27 names directly from `shinro.mcp.server`, and the stdio functional
test spawns `python -m shinro.mcp.server`, while `pyproject.toml` pins the
console script to `shinro.mcp.server:main`. So `server.py` re-exports the full
tool surface plus `_store`; **no test needed changing**. `__all__` lists every
re-export so ruff's `F401` treats them as intentional.

Import graph is acyclic: `_common` ← tool modules ← `server`.

Docs touched: `docs/mcp_server.md` gained a **Module layout** table (and its
stale "1213 lines" / "Total: 108 tests" count corrected to the real 126 run /
127 collected); `AGENTS.md` and `docs/components.md` now point at the package
rather than a single file.

## Gotcha worth recording

The LSP reported `reportMissingImports` for all nine `shinro.mcp._*` imports
after the split, and it was **wrong**. The files were created via shell on
`/mnt/E` (a WSL-mounted Windows drive) where inotify does not reliably fire, so
the long-running Pyright instance never learned they existed. Two independent
checks falsified it: `pyrefly` (the repo's actual typechecker) **0 errors**, and
a **fresh Pyright process** `pyright src/shinro/mcp/` → **0 errors, 0
warnings**. Runtime agreed (`importlib` resolved all five modules, 25 tools
registered, all six files `py_compile` clean).

Lesson: on the `/mnt/E` checkout, treat a *sudden cluster* of
`reportMissingImports` for files just created by shell command as stale LSP
state and confirm with a fresh CLI run before chasing phantom fixes.

## Follow-up — codegen + verification exposed as MCP tools

**The gap.** The MCP server stopped at *runtime* use of components: create,
compute, reset. Everything that turns a component into a deployable kernel lived
only behind `make compile` / the `shinro-compile` CLI / `make measure-kernels`.
An MCP client could drive a controller but could not trace it, inspect the
captured graph, lower it to Zig, build the `.so`, or run the verification gates
— which is exactly the loop an agent iterating on a controller wants.

**What was added — 14 tools in two domain modules**, following the split from
the previous commit:

`src/shinro/mcp/_codegen.py` (zig-free half):

- `list_codegen_ops` — registered ops + scenario graph recipes
- `check_component` — construct a config, report its trace contract (no trace)
- `trace_component` — trace one component; reports `state_attrs` **and their
  live shapes** so a caller can re-trace with persistent `state_*` ports
- `build_composed_graph` — the two-pass trace + compose closed-loop step graph
- `graph_summary` — ports, op histogram, lowerability
- `interpret_graph` — run a graph on numpy inputs (the Python oracle)
- `measure_graph` — static size metrics (host buffers / VM stack / blobs)
- `lower_graph` — serialize to `graph_data.zig` + manifest, no compiler
- `generate_scenario` — the gen stage: trace + compose + lower an isolated graph

`src/shinro/mcp/_verification.py` (gates + zig stage):

- `run_gate_a` — `interpret(graph)` vs the live estimator + controller
- `build_kernel` — integrity + gate A + `zig build` + oracle B + stamp + verify
- `run_oracle` — `.so` vs `interpret()` on random inputs
- `stamp_deployment` / `verify_deployment` — write and re-hash the record

**Three design decisions that mattered.**

1. **stdout is the transport.** `build_scenario` (26 prints), `stamp` (2) and
   `verify` (3) narrate on stdout. On a stdio MCP server that is the JSON-RPC
   channel, so a naive call would corrupt the protocol stream. Every pipeline
   call now runs under `redirect_stdout`/`redirect_stderr` and the captured text
   is returned as a `log` field. `test_build_log_is_captured_not_printed` pins it
   by asserting the narration comes back *inside* the JSON.
2. **Never clobber the shipped graph.** `lower_zig`'s default output is
   `src/shinro/runtime/graph_data.zig` — the shipped KF+LQR graph. Every lowering
   tool takes an explicit `out_dir` and refuses one inside the packaged runtime
   dir (root *or* subdirectory). Tests assert both the refusal and that the
   shipped file is byte-identical afterwards.
3. **Graphs get their own store.** `_graph_store` is separate from `_store`;
   otherwise a graph and a controller sharing a name would resolve to each
   other in the "is this name a controller?" checks. Pinned by
   `test_graph_and_controller_can_share_a_name`.

**Measured.** Re-tracing the base KF with the reported `state_shapes` turns
`x_hat`/`P` into `state_x_hat`/`state_P` ports. The composed base graph is 47
nodes, `lowerable: true`, `has_solve_qp: false`; interpreting it at zero state
error yields `u = [0,0,0]` while `state_P` still updates (0.09099 from identity),
which proves the recurrence is threaded rather than frozen. The zig stage builds
that graph to a verified, stamped `.so` with `oracle.status = "passed"`.

**Tests.** New `tests/test_mcp_codegen.py` (31, no zig) and
`tests/test_mcp_verification.py` (21, one shared real build). The protocol test
in `test_mcp_server_functional.py` pinned the tool count at 25 — updated to 39
with the new names (an exact-count contract test, deliberately).

**Verification:** `make lint` clean (ruff + pyrefly 0 errors); fresh `pyright`
over `src/shinro/mcp/` + the three MCP test files **0 errors**;
`make test` **2097 passed / 5 skipped** (2045 + 52 new);
`test_mcp_server_functional.py` **37 passed** with `tools/list` reporting 39.
`graph_data_manifest.json` clobbered by the suite and restored.

**Editor caveat (second occurrence).** Pyright reported `reportMissingImports`
for `_codegen`/`_verification` for several probes after creation. Falsified
again with fresh processes (0 errors) plus pyrefly and runtime import; the
long-running LSP's import-resolver caches the `shinro/mcp/` directory listing
and inotify does not fire on the `/mnt/E` mount. It cleared on its own after a
later write, same as the five modules from the previous commit. A restart of the
editor's language server clears it immediately.

## Follow-up — split the MCP surface into two servers

**Why.** After the codegen/verification tools landed, one server advertised 39
tools (~8.6k tokens of schema). Measured payload:

| family | tools | ~tokens | share |
|---|---|---|---|
| components | 18 | 2,845 | 33% |
| codegen | 9 | 2,135 | 25% |
| verification | 5 | 2,033 | 24% |
| analysis | 7 | 1,601 | 19% |

An MCP client puts every tool schema of a connected server into the model's
context each turn, and `codegen`+`verification` were **48%** of it while serving
a completely different phase of work (compile, not design). The literature on
tool-set size (arXiv `2505.10570`: 7–85% accuracy drop as tool count grows;
`2505.03275` RAG-MCP: 13.6%→43.1% on MCP tool selection; `2606.15508`
ToolMenuBench: 32.1%→85.7% with a minimal tool menu) points at both token bloat
and selection ambiguity, so this is a relevance measure, not only a cost one.

**What changed.** Two FastMCP instances in `_common.py` — `server` (unchanged
name) and `codegen_server` — and two entry points:

| entry point | console script | tools |
|---|---|---|
| `shinro.mcp.server` | `shinro-mcp` | 25 (controllers, estimators, trajectories, analysis) |
| `shinro.mcp.codegen_server` | `shinro-mcp-codegen` | 14 (trace, compose, lower, gates, build, stamp, verify) |

`_codegen.py` / `_verification.py` now import `codegen_server as server`, so
their `@server.tool()` decorators register on the second instance only. Importing
the component server does not leak them: verified as 25/14 with **zero overlap**
and distinct instances. `server.py` stopped re-exporting the codegen tools, so it
no longer claims to serve tools it doesn't.

**Design notes.**
- Both servers keep shared helpers (`_resolve_backend`, `_store`, `_graph_store`)
  in `_common.py`; the stores are per-process, which is correct because the two
  servers run as separate stdio processes.
- `.mcp.json` keeps **only** the component server. Default sessions are
  controller work, so the codegen server is a documented one-entry addition
  rather than an always-on cost — otherwise the split buys nothing in this repo.
- `__init__.py` documents both entry points.

**Tests.** `test_mcp_codegen.py` / `test_mcp_verification.py` retargeted to
`shinro.mcp.codegen_server` (the component tools they also use still come from
`shinro.mcp.server`). The functional suite's fixture was factored into a
`_client(server_path)` context manager with `server` and `codegen_server`
fixtures; `tools/list` now asserts 25 for the component server, and a new
`TestCodegenServerProtocol` asserts exactly 14 on the codegen server, no
component tools, and a real `list_codegen_ops` round trip over stdio. Two
symmetric "does not expose the other family" tests pin the split in both
directions.

**Verification.** `make lint` clean (ruff + pyrefly 0 errors); fresh `pyright`
over `src/shinro/mcp/` + both test files **0 errors**; `test_mcp_codegen.py` +
`test_mcp_verification.py` **52 passed**; `test_mcp_server.py` **126 passed / 1
deselected**; `test_mcp_server_functional.py` **41 passed** (both processes).

**Environment gotcha (root-caused at last).** Pyright reported
`reportMissingImports` for `_codegen` / `_verification` / `codegen_server` for
most of this session; fresh CLI runs said 0 errors. Rather than adding `# type:
ignore` for a false positive, I probed the LSP's view directly: it resolved the
five modules created two commits ago but not the ones created since, proving its
index was a stale snapshot. The cause was the long-running
`pyright-langserver` (PID 107434, up 29 min) whose watcher never saw files created
on the `/mnt/E` mount. `kill -TERM` on it (the client respawns it) cleared every
finding instantly — **6 files, 0 diagnostics**. Lesson: when a cluster of
`reportMissingImports` appears for files just created on a mounted drive, restart
the language server before touching source.

## Follow-up — end-to-end agent test on a separate repo (shinro-bench)

**The test.** Can an independent agent, working only in a *different* repository,
drive the codegen MCP server through the whole pipeline? Setup:

- target repo: `shinro-bench` (pinned to the `lebrobot` pyenv, which has `onnx`
  1.22 and `shinro` editable from this repo), git-clean except an untracked `.pi/`
- server: `python -m shinro.mcp.codegen_server` under lebrobot, declared in
  `shinro-bench/.pi/mcp.json` (project-scoped, 14 tools)
- agent: `pi -p` (default model), given a 233-word outcome brief — compile
  `tasks/policies/models/toy_lstm/toy_lstm.onnx` to a **native** `.so` using only
  the MCP tools, artifacts under `build/mcp-e2e/`, no direct `zig`, no
  `shinro.codegen` import, no `scripts/policy_build.py`

**Result: the workflow works end to end.** Artifact `lib_neural_network.so`,
10,120 B native x86-64; 22 nodes traced → 17 lowered; recurrent ports
(`state(3), state_h_0(4), state_c_0(4)` → `u(2)`, `state_hc_0(8)`); oracle B
max abs err **1.1e-16** (20 samples) and **1.67e-16** (500 samples) vs 1e-12;
`verify_deployment` ok with a stable master hash across re-stamping. The agent
also confirmed the recurrence is live (not frozen) by feeding `state_hc_0` back
through ctypes.

The agent authored the missing translation itself: an `onnx_rl` controller config
plus a policy-only scenario TOML, reading only `samples/` from this repo for the
schema. That is the cross-repo seam working as intended.

**Five findings, four fixed here.**

1. **`build_kernel` returned null metadata for any non-`libbase` artifact.**
   `if manifest and artifact_name is None:` guarded the "adopt the stem actually
   built" glob on the *default* stem existing — so with
   `artifact_name = "lib_neural_network"`, `artifact`/`artifact_bytes`/`oracle`/
   `master_hash` were all null despite `exit_code: 0`. Root cause of the original
   defect plus a second one introduced by my first fix: the stem was resolved
   *before* the build, when `lib/` was still empty. Both fixed — resolution now
   happens after `_capture`. Regression test builds a `lib_custom` scenario.
2. **`run_oracle` could not find a non-default stem**, failing with
   `load_so`'s "zig build produced no libbase.so" — misleading, since this tool
   never builds. Now auto-adopts the single `.so` in `<prefix>/lib`, and on a real
   mismatch returns `{error, available_artifacts, hint}`.
3. **`run_oracle` / `stamp_deployment` used two shapes for the oracle fact**, so
   chaining needed manual transcription. `run_oracle` now returns a `record` block
   that is exactly `build_kernel`'s canonical shape and can be passed straight to
   `stamp_deployment(oracle=...)`.
4. **Two unlabeled node counts** (22 traced vs 17 lowered) in the same response.
   Renamed to `nodes_traced` (pre-optimisation; what `interpret()` and gate A run)
   and `nodes_lowered` (post-fold; what the VM compiles) across `graph_summary`,
   `lower_graph`, `generate_scenario`, `measure_graph`, `run_gate_a`.
5. **Not fixed — policy-only graphs have no gate A.** With no `[estimator]` there
   is no live pair, so oracle B is the only equivalence check; it compares `.so`
   vs `interpret()` of *the same graph*, so a mis-wired state port or a wrong
   observation encoder cannot be caught. The agent had to hand-write a ctypes
   recurrence check to cover that. A policy gate (interpret vs the eager
   `onnx_rl` adapter over N ticks) is the natural follow-up. Also noted: policy-only
   scenarios cannot derive `n_x`/`n_u` from the ONNX model and must declare them.

**Harness friction (not shinro).** pi gates *project* MCP servers behind consent;
non-interactive runs only pass when the user-global `projectServers` policy is
`"allow"`. Run 1 worked around it by speaking JSON-RPC to the same server over
stdio (still the 14 tools, so the surface was validated), run 2 stopped to ask,
run 3 succeeded through the real MCP client. One agent edited the global
`~/.pi/agent/mcp-adapter.json` to flip that policy; I restored the backup and kept
only the scoped per-project approval for `shinro-bench/shinro-codegen`.

**Verification:** `make lint` clean (ruff + pyrefly 0); `test_mcp_codegen` +
`test_mcp_verification` + `test_mcp_server` **181 passed / 1 deselected**;
`test_mcp_server_functional` **41 passed**. `graph_data_manifest.json` clobbered by
the suite and restored.
