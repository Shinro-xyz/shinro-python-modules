# 2026-10-19 — Split the MCP server into per-domain modules

Branch: `refactor/mcp-server-split`

## Why

Two questions came up, in order:

1. **Does the MCP server belong in this repo at all, or in its own repo?**
   Answer: keep it here. `src/shinro/mcp/server.py` imported only the public
   factory surface (`ControllerFactory`, `EstimatorFactory`,
   `TrajectoryFactory`, the registries, `NumpyBackend`/`TorchBackend`,
   `LTISystemsAnalyzer`) — nothing in core imports *from* `mcp/`, so it is a
   facade over the library, not a subsystem. The decisive argument is the tool
   surface: `list_controller_types()` / `list_estimator_types()` /
   `list_trajectory_types()` just dump the registries, so any component added
   to shinro shows up in the MCP tools for free. A separate repo would need a
   coordinated release per component and would drift. It would only earn its
   own repo if it grew past a facade (remote transport, auth, hosting) — that
   is an infrastructure concern, not a client-library feature.
2. **The file itself was the problem:** 785 lines holding four tool families
   plus shared helpers, and the four sections were already marked with banner
   comments — i.e. the split was latent in the file.

## Change

`src/shinro/mcp/` split by domain, with **zero logic changes** — every tool
body was moved verbatim (sliced from the original by section anchor, not
retyped):

| Module | Lines | Contents |
|--------|-------|----------|
| `_common.py` | 63 | `server` (the single `FastMCP` instance), `_store`, `_resolve_backend`, `_to_list`, `_from_list`, `_set_mpc_default_constraints`, `_make_analyzer` |
| `_controllers.py` | 218 | create / compute / reset, MPC constraints, PID limits, listing (8 tools) |
| `_estimators.py` | 106 | create / estimate / reset, listing (5 tools) |
| `_trajectories.py` | 159 | create / generate / position_at, listing (5 tools) |
| `_analysis.py` | 270 | controllability, observability, 3× Gramians, summary, balanced truncation (7 tools) |
| `server.py` | 103 | imports the tool modules for registration, re-exports every tool + `_store`, `main()` |

**The load-bearing constraint — one store, one server.** `_store` and `server`
must be the *same objects* everywhere, or the tests' `clear_store` fixture
would clear a different dict than the tools read, and tools would register
against a stray `FastMCP`. They are defined once in `_common.py` and imported
(never re-created) by the tool modules; `server.py` re-exports the same names.
Pinned by an identity assertion during development (`server is
_common.server`, `_store is _common._store`).

**The second constraint — import compatibility.** `tests/test_mcp_server.py`
imports 27 names directly from `shinro.mcp.server`, and the stdio functional
test spawns `python -m shinro.mcp.server`, while `pyproject.toml` pins the
console script to `shinro.mcp.server:main`. So `server.py` re-exports the full
tool surface plus `_store`; **no test needed changing**. `__all__` lists every
re-export so ruff's `F401` treats them as intentional.

Import graph is acyclic: `_common` ← tool modules ← `server`.

Docs touched: `docs/mcp_server.md` gained a **Module layout** table (and its
stale "1213 lines" / "Total: 108 tests" count corrected to the real 126 run /
127 collected); `AGENTS.md` and `docs/components.md` now point at the package
rather than a single file.

## Verification

- **Baseline first** (before touching anything): `test_mcp_server.py` **126
  passed / 1 deselected**; `test_mcp_server_functional.py` **37 passed**; 25
  tools via a raw JSON-RPC `tools/list`.
- **After the split** — the tool list is **byte-identical** (diffed
  `tools/list` output before vs after: same 25 names), proving the
  `@server.tool()` side-effect registration survived the move.
- `tests/test_mcp_server.py` **126 passed / 1 deselected** (unchanged).
- `tests/test_mcp_server_functional.py` **37 passed** (stdio handshake +
  protocol-level calls against the real subprocess).
- `make lint` clean (ruff + pyrefly 0 errors).
- `make test` **2045 passed / 5 skipped** — identical to main, no regressions.
- Ruff raised 6 issues on the freshly generated files (5× `I001` isort
  ordering, 1× `F401` — `typing.Any` became unused in `_controllers.py` once
  `_set_mpc_default_constraints` moved to `_common`); fixed with `ruff check
  --fix` + `ruff format`.
- `src/shinro/runtime/graph_data_manifest.json` was rewritten by the suite (the
  documented shared-generated-path effect) and restored to HEAD, so the commit
  contains only intended files.

## Gotcha worth recording

The LSP reported `reportMissingImports` for all nine `shinro.mcp._*` imports
after the split, and it was **wrong**. The files were created via shell on
`/mnt/E` (a WSL-mounted Windows drive) where inotify does not reliably fire, so
the long-running Pyright instance never learned they existed. Two independent
checks falsified it: `pyrefly` (the repo's actual typechecker) **0 errors**, and
a **fresh Pyright process** `pyright src/shinro/mcp/` → **0 errors, 0
warnings**. Runtime agreed (`importlib` resolved all five modules, 25 tools
registered, all six files `py_compile` clean).

Lesson: on the `/mnt/E` checkout, treat a *sudden cluster* of
`reportMissingImports` for files just created by shell command as stale LSP
state and confirm with a fresh CLI run before chasing phantom fixes.
