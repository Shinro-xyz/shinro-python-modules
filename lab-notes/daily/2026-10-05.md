# 2026-10-05 — Extended Kalman filter: predict/update, Jacobians, TOML config, tests

Branch: `main`

## Why

`src/shinro/estimators/extended_kf.py` held only a constructor stub, and it was
**unimportable**: it carried `@register_estimator("ExtendedKalmanFilter")` but no
frozen `Config`, and `register_estimator` is `strict=True`, so the decorator
raised `TypeError` on import. The module was not re-exported from
`estimators/__init__.py`, so nothing had ever tripped over it. The task: fill in
the EKF math (including the Jacobians), add TOML config support, and test it.
This closes the first item of issue #18 (component backlog → Estimators → EKF).

## Math decisions

**Continuous-time process model.** `dynamics_fn(x, u) -> dx/dt`, matching
`Plant.dynamics` and the nonlinear plants (CartPole, InvertedPendulum) added on
2026-07-27 explicitly "as the hook for future … estimators (EKF, UKF)". The
filter Euler-discretizes at `dt`, so the discrete process Jacobian is
`F = I + dt · ∂f/∂x` — the same convention as
`shinro.utils.linearization.discretize_euler`. This is also what makes the
stub's `dt` argument meaningful.

**Flat-vector convention.** State `(n_x,)`, control `(n_u,)`, measurement
`(n_y,)` — the rest of the stack (controllers, plants, `BatchedDynamicsAdapter`)
is flat, `ArrayBackend.jacobian` is flat-native, and the compose layer has to
insert reshapes to reconcile the KF's `(n,1)` column vectors with the flat
controller inputs (`codegen/compose.py:177,186`). Choosing flat avoids that
special-casing for new code.

**The control Jacobian is never needed.** The EKF treats `u` as known exactly,
so `∂f/∂u` does not enter the covariance. This dissolves the earlier
"how do we know `n_u`" problem entirely: the filter only needs `n_x` (from `Q`
or `x0`) and `n_y` (from `R`).

**Predict:**

```text
x⁻ = x̂ + dt·f(x̂, u)
F  = I + dt·∂f/∂x|_x̂
P⁻ = F P Fᵀ + Q
```

**Update:**

```text
H  = ∂h/∂x|_x⁻
S  = H P⁻ Hᵀ + R
K  = P⁻ Hᵀ S⁻¹
x̂  = x⁻ + K (y − h(x⁻))
P  = (I − K H) P⁻
```

## What was built

- `ExtendedKalmanFilter.__init__` now takes `dynamics_fn`, `measurement_fn`,
  `dt`, `Q`, `R`, optional `x0`, and a backend. Fixed the `NumpyBackend` (class,
  uncalled) → `NumpyBackend()` bug.
- `_dynamics_jacobian` / `_measurement_jacobian`: **always auto-computed** via
  `self.bk.jacobian(f, x)` (central finite differences on numpy, autograd on
  torch). No analytical Jacobian is accepted — `dynamics_fn` and
  `measurement_fn` are the only model inputs. Each closes over `u` so only the
  differentiation variable is free, and flattens inside the closure so a
  `(n,1)`-returning model can't broadcast into an `(n,n)` Jacobian.
- `_flat` guards the measurement/control against the silent `(n,) − (n,1)`
  broadcast that would otherwise corrupt the innovation.
- `_callables` centralizes the "callables not injected" guard so the type
  checker sees the narrowing; `estimate` raises a clear `RuntimeError` when
  neither was injected.
- `ExtendedKalmanFilterConfig` (frozen dataclass) + `from_config`: `Q` from
  `process_noise`, `R` from `measurement_noise`, optional `dt` (plant-injected
  in scenario builds) and `initial_state`. The callables are not
  TOML-serializable, so they start `None` and are injected after construction —
  the same pattern as MPPI's `dynamics_fn`/`cost_fn`.
- Exported `ExtendedKalmanFilter` from `estimators/__init__.py`.
- `samples/estimators/ekf_base.toml` seed config.

## Tests

`TestExtendedKalmanFilter` in `tests/test_estimators.py` — 15 tests run on both
the numpy and torch backends, plus a registration/export check:

- shape (flat `(n_x,)`), reset (zero and explicit `x0`);
- **linear equivalence**: EKF reproduces a `KalmanFilter` with
  `A_d = I + dt·A_c`, `B_d = dt·B_c`, `C`, `D = 0` — matched to ~1e-12 (the
  auto-computed Jacobian's roundoff on a linear model), and `P` likewise;
- one-step predict/update vs a hand-rolled reference (atol 1e-8);
- the **auto-computed** Jacobian vs analytic for `f` and for a nonlinear
  `h(x) = [x₀², x₁]` (expected `[[2x₀, 0], [0, 1]]`);
- **nonlinear convergence**: constant state with `h(x) = x²`, estimate
  converges to the true state 2.0 (error < 1e-3; actual ~1e-11);
- column-vector `(n,1)` inputs are flattened, not broadcast;
- `from_config` shapes/defaults, full-matrix + `initial_state` parsing, inject-
  then-estimate, missing-`dt` and unknown-key rejection, and the shipped
  `ekf_base.toml` parsing.

## Caveats

- **Not lowerable, by design.** The EKF auto-computes its Jacobians via
  `bk.jacobian`, which `TraceBackend` does not implement
  (`codegen/trace_backend.py:402` raises `missing_op_error` for unknown
  methods); the finite-difference path is also a per-sample scalar loop that
  cannot be traced. The optional analytical-Jacobian override was deliberately
  **removed** to keep the model surface to `dynamics_fn`/`measurement_fn` only,
  so a compiled/served EKF would need the Jacobian expressed as a traceable
  graph (`bk.*` ops) at the codegen layer — not an injected callable. Mirrors
  MPPI's documented trace-safety gap.
- Two pre-existing `possibly unbound` pyrefly findings remain in the untouched
  `test_estimate_converges_1d` bodies (Kalman/Luenberger); left alone as
  out-of-scope. They are not in the repo's `make lint` pyrefly scope (tests/).

## 2026-10-05 (later) — Batched FD Jacobian on the trace backend: the EKF becomes lowerable

Branch: `feat/estimator-additions`

### Why

The EKF note above closed with a caveat: the filter is **not lowerable** because it
auto-computes its Jacobians through `bk.jacobian`, which `TraceBackend` does not
implement — so a compiled/served EKF had no route. This slice adds that op at the
trace layer (no VM/kernel changes) and measures what it costs.

### What was built

`TraceBackend.jacobian(f, x, eps=1e-6, *, batched=True)` in
`src/shinro/codegen/trace_backend.py`. It captures a **central** finite-difference
Jacobian of a traced callable as graph nodes, mirroring `NumpyBackend.jacobian`
(shape `(m, n)`, same `eps`).

The design decision — the thing that makes it cheap — is that the perturbation is
**batched**:

```text
X  = reshape(x, 1, n) + vstack([+eps*I, -eps*I])   # (2n, n), one broadcast add
F  = f(X)                                          # f-subgraph emitted ONCE
J  = ((slice(F,0,n) - slice(F,n,2n)) / (2*eps)).T  # 2 slices + sub + mul + T
```

So the derivative costs `|f| + ~6` nodes instead of `2n_x * |f|`. It rides the
**batch axis the model is already written in** — `Plant.dynamics` is batch-capable
by contract (`(N, n_x) -> (N, n_x)`, the same property MPPI's rollout depends on), so
the probes are just a wider evaluation of the same subgraph. This is the "kernel
fusion" for a Jacobian: not a fused kernel, but batching the probes into one
subgraph evaluation.

Two contracts, both enforced loudly with `ShapeMismatchError`:
- `x` must be 1-D (the numpy backend's silent 2-D misbehaviour is not mirrored);
- a batched callable must accept a leading probe axis and return `(2n, m)` — a
  non-batch-capable callable (e.g. an arbitrary user `measurement_fn`) is told to
  wrap it or pass `batched=False`, the per-column escape hatch (same arithmetic,
  `2n` emissions).

### Measured cost (ReleaseFast x86-64; total nodes / `.so` KiB / median `shinro_step`)

EKF-only graphs (H = const linear `C`), duplicated per-column FD vs the batched probe:

| plant | n_x | dup nodes / KiB / µs | batched nodes / KiB / µs | node cut |
| --- | --- | --- | --- | --- |
| InvertedPendulum | 2 | 189 / 231 / 0.9 | 101 / 223 / 1.0 | 1.9× |
| CartPole | 4 | 595 / 299 / 1.6 | 165 / 257 / 1.5 | 3.6× |
| DoublePendulum | 4 | 649 / 298 / 1.5 | 177 / 253 / 1.3 | 3.7× |
| Quadrotor | 12 | 4404 / 811 / 6.2 | 391 / 319 / 4.5 | 11.3× |

Cold ReleaseFast compile: 13.3 s → 4.5 s at the quadrotor. The tick win is modest
(1.0–1.4×, and batching is a hair *slower* at n_x=2) because the FLOPs are unchanged;
the win is node count, `.so` size, compile time, and instruction-cache pressure.

**Correction to the earlier reasoning in this file's sibling analysis:** the "~1 µs
node" figure is for wide-matmul policy graphs (H=128). EKF nodes carry ≤12 elements
and run at ~1.5–2 ns/node, so the central-FD quadrotor EKF is **6.2 µs/tick on x86**,
not the ~3.6 ms I had extrapolated — even a 10× slower Pi is ~60 µs, comfortably
inside 1 kHz. FD never threatened the deadline; it was a bad per-node constant, not a
bad method.

### Parity

- Batched vs per-column: identical per-probe arithmetic; **bit-identical** for
  elementwise-only models (the plant dynamics — measured `max|Δ| = 0.0`), and within
  ~`1/(2eps)`=5e5 ulps when a shape-sensitive kernel (BLAS matmul) is in the model
  (measured 2.2e-10), since the probe batch changes its blocking.
- Real-method end-to-end (CartPole / Quadrotor): `interpret` vs eager `0.0`, compiled
  `.so` vs eager `0.0` / `1.4e-17`.

### Tests

`TestTraceBackendJacobian` (7 tests) in `tests/test_codegen.py`: batched matches
`NumpyBackend.jacobian` (atol 1e-12), dup mode matches, batched-vs-dup agreement
(roundoff tol), batched emits **one** model subgraph (sin/matmul counted), linear-map
orientation (`d(x@W)/dx == W.T`), non-batch-capable callable raises, 2-D point raises.

### Not done (next slice)

- `ExtendedKalmanFilter.estimate()` still calls `dynamics_fn(x, u)` / `measurement_fn(x)`
  **without forwarding `self.bk`** (tracing falls back to the plant's numpy backend and
  dies on a `Tracer`), and the probe closure must pass a 2-D batch through instead of
  squeezing via `_flat`. Both are required before a real EKF scenario can compile; the
  measurements above used an instance-level patch for them.
- No `measurement_matrix` config key yet (H is currently FD'd unless patched to const `C`;
  the TOML `C` costs 3 nodes vs ~36 for FD).
- No compiled EKF scenario TOML / integration test yet; no analytic `jacobian_x` plant
  hook (now a late optimisation, not a requirement).
